## 问题

### 🔴 阻塞问题

1. **[架构] Domain 层 SyncExportService 直接依赖 Data 层 TuneHavenPackager**

   `SyncExportService` 在 Domain 层，`TuneHavenPackager` 在 Data 层。Domain 不应直接依赖 Data 层实现类。

   → 修复：在 Domain 层定义 `SyncPackaging` 协议，`TuneHavenPackager` 实现该协议。Service 通过协议注入。

2. **[架构] TuneHavenPackager 分层错误**

   `TuneHavenPackager` 做的是 ZIP 文件 I/O 操作，属于基础设施，应放在 Core 层而非 Data 层。Data 层应只包含 CoreData 相关实现。

   → 修复：`TuneHavenPackager` 移至 `Core/Storage/`。

3. **[逻辑] 缺失歌曲引用的 playlistId 创建时机**

   导入歌单时，如果是新歌单（无冲突或选择新建副本），歌单的 UUID 在 CoreData 创建后才确定。但 `MissingSongReference` 需要 `playlistId`。方案中未说明这个时序。

   → 修复：明确流程为「先创建歌单 → 获取新 UUID → 再创建 MissingSongReference」。

### 🟡 重要问题

4. **[性能] 匹配引擎对每首歌调用 fetchAll**

   `matchSong()` 内部调用 `songRepo.fetchAll()`，如果批量导入 100 首歌就要查询 100 次全表。

   → 修复：在 `analyze()` 阶段一次性 fetchAll 并缓存为字典（key 为 `title+artist`），匹配时直接查字典。

5. **[清晰度] 歌单冲突「替换」的具体行为未定义**

   「替换」是保留原歌单 UUID 只替换歌曲列表？还是删除旧歌单再创建新的？前者保持引用稳定，后者更简单。

   → 修复：明确为「保留原歌单 UUID 和基础信息，清空旧歌曲列表后填入新歌曲列表，更新歌单名称/描述/封面」。

6. **[边界] .tunehaven 包内文件名冲突**

   两首不同歌曲可能有相同文件名（如不同专辑的 `01.mp3`）。打包时会覆盖。

   → 修复：打包时文件名加序号前缀（如 `0001_01.mp3`），`SongExportData.audioFileName` 存储包内路径而非原始文件名。

### 🟢 轻微问题

7. **[清晰度] 批量歌曲导出的分享方式**

   `exportSongs` 返回 `[URL]` 用于分享。但批量分享多个文件时 AirDrop 体验较差。

   → 修复：批量歌曲导出也打包为 `.tunehaven` 文件（`contentType = .songs`），保持一致的分享体验。

8. **[规范] SyncContentType 的 Codable 支持**

   枚举默认 Codable 合成需要 String/Int RawValue。当前无 RawValue 声明。

   → 修复：改为 `enum SyncContentType: String, Codable`。
