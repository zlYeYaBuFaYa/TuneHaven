# 方案：软删除后重导（Review T4）

> 创建日期：2026-11-17 | 状态：已完成

## 1. 需求概述

删除歌曲后，记录先被标记为 `softDeleted = YES`，30 秒后（或 App 被杀后的下次启动）才真正删除。在这个窗口内重新导入同一个文件：

- `ImportService` 用 `fetchByHash`（只查未删除记录）去重，认为是新歌，复制文件后调用 `CoreDataSongRepository.insert`；
- `insert` 按 `fileHash` 查找时**包含**软删除记录，命中后只更新元数据：记录仍是软删除状态，`id` 仍是旧值；
- 结果：导入显示成功但歌曲不出现；返回的 `song.id` 在库里不存在；随后 `commitDelete` 删掉这条记录，新复制的文件成为孤儿；若由 `cleanupPendingDeletes` 处理，还会删除同路径的新文件。

目标：软删除窗口内重导同一文件，得到一条可见的新歌曲记录，`id` 与导入结果一致，之后的提交删除、撤销、启动清理都不会影响它。

范围：只修此高危项。「删除提交依赖 30 秒 Timer」的中危项不在本次范围。

验收标准：

1. 删除后 30 秒内重导同一文件：曲库可见，`fetchSong(id: 导入结果 id)` 能取到。
2. 随后 30 秒提交（`commitDelete`）不删除新记录。
3. 启动清理（`cleanupPendingDeletes`）不删除新记录。
4. 未删除的同哈希记录仍按原行为更新，不产生重复记录。

## 2. 现状分析

| 文件 | 现状 |
|------|------|
| `Data/Repositories/CoreDataSongRepository.swift` `insert(song:)` | `fileHash == %@`、`fetchLimit = 1`，命中即 `updateEntity` |
| `commitDelete(token:)` | 按 token 的旧 id 删除记录和歌单链接，再删 pending 目录中的文件 |
| `cleanupPendingDeletes()` | 处理 `softDeleted == YES AND deletedAt < now-30s` 的记录，按哈希无活跃引用时删除 Music 下对应路径 |
| `undoDelete(token:)` | 按旧 id 恢复记录；原路径文件不存在时把 pending 文件移回 |
| `Core/Persistence/CoreDataStack.swift` | 只有单例，`private init`，无法在测试中使用内存库 |
| 测试 | 没有 Core Data 仓储测试，`MockSongRepository.insert` 只 append |

## 3. 技术方案

### 3.1 整体设计

`insert` 在后台上下文中按 `fileHash` 取出**全部**同哈希记录：

```
active  = softDeleted == NO 的记录
deleted = softDeleted == YES 的记录

for e in deleted:
    删除 PlaylistSongEntity(songId == e.id)
    删除 e
if let first = active.first:
    SongMapper.updateEntity(first, from: song)   // 原行为
else:
    SongMapper.toEntity(song, context:)          // 用导入给出的新 id
```

旧记录被硬删后：

- `commitDelete(token)`：按旧 id 找不到记录，只删除 pending 目录里的旧文件，不碰新文件。
- `undoDelete(token)`：按旧 id 找不到记录；原路径已有新文件时跳过移回（同名同哈希，路径相同）；路径不同时旧文件被移回原位，成为无记录文件，不影响新歌曲（见风险）。
- `cleanupPendingDeletes()`：旧记录已不存在，不会进入删除分支。

`PlayRecordEntity` 不删除，与现有 `commitDelete` 一致；`fetchRecentlyPlayed` 只返回存在且未删除的歌曲，旧 id 的播放记录不会显示。

### 3.2 详细实现

**CoreDataSongRepository.insert(song:)**：按上面伪代码改写，删除 `fetchLimit = 1`。

**CoreDataStack**（测试支持）：

- 新增 `private init(container:)`，单例 `init()` 改为调用它。
- 新增 `#if DEBUG` 的 `static func makeInMemory() async throws -> CoreDataStack`：复用 `CoreDataStack.shared.container.managedObjectModel`（避免同一进程加载两份模型导致实体类冲突），存储描述为 `NSInMemoryStoreType`，加载后同样创建后台上下文。

### 3.3 备选方案

复活旧记录（保留收藏、播放次数、歌单链接）需要同时作废待提交的 undo token，否则 30 秒后会把复活的记录硬删，仓储层还要反向通知 `MusicLibraryService`。用户已确认采用硬删重建。

## 4. 影响范围

- 只改 `insert` 的同哈希处理；导入流程、`ImportService`、界面不变。
- 无数据模型变更。
- 重导后的歌曲是全新记录：不继承旧记录的收藏、播放次数、歌单归属（旧记录本就已被用户删除）。

## 5. 测试要点

新增 `TuneHavenTests/CoreDataSongRepositoryTests.swift`，使用内存库：

1. 普通插入后可按 id 取到。
2. 同哈希的未删除记录存在时插入：只更新、不新增，总数仍为 1。
3. 软删除后重导：新 id 可取到，`fetchByHash` 返回新 id，旧 id 取不到，`fetchAll` 只有 1 条。
4. 旧记录的歌单链接被清除。
5. 重导后执行旧 token 的 `commitDelete`：新记录仍在。
6. 软删除后先把旧记录的 `deletedAt` 改到 1 分钟前（模拟已过撤销窗口），再重导，再执行 `cleanupPendingDeletes`：新记录仍在。

回归：全量 `TuneHavenTests`。

## 6. 风险评估

| 风险 | 应对 |
|------|------|
| 重导文件名与原文件不同、用户随后点「撤销」 | 旧文件被移回原路径但无记录，占用磁盘但不影响功能；属于少见操作，记录为已知限制 |
| 内存库测试与真实 SQLite 行为差异 | 只测谓词与增删，内存库语义一致 |
| `cleanupPendingDeletes` 测试会调用 `FileStorageService.shared.cleanupPendingDeleteDirectory()` 清理测试宿主的 pending 目录 | 测试宿主无用户数据，可接受 |
