## 1. 需求概述

- 场景：音乐库「全部 / 艺术家 / 专辑」搜索；歌单详情内搜索使用同一套字段匹配。
- 字段：歌曲名、艺术家、专辑。
- 原文：`trim` + `lowercased()` 后 `contains`。搜索「里香」「曲」仍能命中「七里香」「夜曲」。
- 全拼：拉丁 query 长度 ≥ 2 时，按**音节起点**做前缀匹配。`zhou` / `zh` 命中「周杰伦」，`qili` 命中「七里香」。
- 首字母：长度 ≥ 2 的连续包含。`qlx`、`ql` 命中「七里香」，`zjl`、`zj` 命中「周杰伦」。
- 模糊：拉丁 query 长度 ≥ 3，且与**整段**全拼或**整段**首字母的长度差不超过 1 时，允许 Levenshtein 距离 ≤ 1。`qilixian`、`zjk` 可以命中；`zg`（长度 2）不可以。
- 长度 1 的拉丁字母不进拼音索引。`a` / `z` 仍只走原文 `contains`，避免单字母扫过半个曲库。
- 空 query：不搜索，音乐库继续展示历史。无结果时轻提示「试试拼音首字母」。
- 多音字取系统常用音；简繁按库存字形生成，不联网转写。
- 无汉字可读的符号曲名只走原文 `contains`。
- 不改左滑删除、收藏、加歌单、历史条数和 Premium 门禁。

## 2. 现状分析

## 3. 技术方案

### 3.1 整体设计

匹配规则放在 Domain 的无状态枚举 `PinyinSearchMatcher`，不进 Service 协议，也不进 UI。`SearchService` 与歌单页只负责调用。

拼音来自 Foundation：

1. `applyingTransform(.mandarinToLatin)`
2. `applyingTransform(.stripDiacritics)` 去掉声调
3. 按非 ASCII 字母数字切音节，得到全拼、首字母和音节起点

拉丁原文会原样落进全拼（`Perfect` → `perfect` / 首字母 `p`），因此英文笔误也能走同一套模糊规则。多音字只保留系统给出的一个读音。

### 3.2 详细实现

`prepare` 把 query 规范成：

- `raw`：trim + lowercased，给原文 contains
- `latin`：去声调后只留 ASCII 字母数字（空格、标点去掉）。`qi li` 与 `QLX` 变成 `qili` / `qlx`
- `allowsFuzzy`：`latin.count >= 3`

`matches` 顺序：

1. `normalized.contains(raw)`（汉字子串、拉丁子串，和现在一致）
2. `latin.count < 2` 则结束
3. 从每个音节起点看全拼是否以 `latin` 为前缀
4. 首字母串 `contains(latin)`
5. 若允许模糊：整段全拼、整段首字母各自做一次编辑距离 ≤ 1（长度差 > 1 直接否定）

编辑距离只算插入、删除、替换，相邻对调算 2，不命中。

音节对齐是为了避免全拼裸 `contains`：`yue` + `de` 会拼出子串 `ed`，查询 `Ed` 会误中「十一月的萧邦」，现有「Ed Sheeran 恰好 2 首」的测试会被破坏。首字母模糊不做滑窗，是为了避免 `soy` 和 `syy…`、`you` 和 `yu` 这种长度 3 的误命中。代价是：只打了长专辑名中间一段、又写错一个字母时，不保证命中；打完整段全拼少一个字母（`shiyiyuedexiaoban`）仍然可以。

缓存：`NSLock` + 字典，键是原始展示字符串。搜索在 `Task.detached` 里读缓存，锁内不调用 Transform。不在启动时预热，避免拖首屏。

歌单页在一次 `body` 计算里只 `prepare` 一次，再过滤。空 query 仍显示全部歌曲。

### 3.3 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 内存缓存 | 无迁移；改标题后自然换新键；实现面小 | 进程重启后第一次搜索要现算 | **采用** |
| Core Data 冗余列 | 二次启动不用重算 | 要迁移；导入和改元数据的每条写路径都得维护，漏一处就是脏结果 | 不采用。万级曲库的 Transform 是一次性成本，有缓存后过滤本身只是字符串比较 |
| 全拼任意子串 + 滑窗模糊 | 实现更短 | `Ed` 误伤中文专辑；3 字母模糊噪声大 | 不采用 |
| 引入拼音词库包 | 可枚举多音 | 工程目前无第三方依赖，且要联网或打大词库 | 不采用 |

## 4. 影响范围

- 音乐库搜索结果会变多（拼音和模糊命中），原文 contains 的命中不会变少。
- 艺术家 / 专辑 Tab 的歌曲列表按该字段的拼音规则收窄；分组数据源不变。
- 歌单内搜索同步变宽。批量添加、分享选歌、Apple Music 导入保持原 contains。
- 无数据库迁移，旧库直接可用。
- Free / Premium 都走这条路径，不调用 `SubscriptionService`。

## 5. 测试要点

- 系统 Transform：`七里香` → `qilixiang` / `qlx`，`周杰伦` → `zhoujielun` / `zjl`；繁体 `週傑倫` 与简体键一致。
- 规则（手写音节，不依赖 Transform）：全拼、首字母、长度 1 不进拼音、长度 2 不模糊、编辑距离 1（替换 / 插入 / 删除）、距离 2 与对调不命中、符号曲名、大小写和空格。
- `SearchService`：`qlx`、`zjl`、`zjk`、`里香`、`曲`；`Ed` 仍然只有 Ed Sheeran 的 2 首；`z` 不命中周杰伦。
- 艺术家 Tab 的 `zjl` 歌曲列表仍是周杰伦；专辑 Tab 的 `qlx` 能命中专辑名。
- 回归：空 query、空白、大小写、历史接口不改，原有搜索测试除写错的那条外保持通过。

## 6. 风险评估

| 风险 | 应对 |
|------|------|
| 系统罗马字没有按音节加空格，首字母会退化成一个字母 | 单测锁死 `qlx` / `zjl`。若失败，再补音节切分，不改匹配语义 |
| 第一次在大曲库上搜索要算拼音，主线程歌单过滤可能顿一下 | 缓存按字符串复用；音乐库过滤放在现有后台 Task 里。万级验证留到真机 |
| 多音字读错 | 接受，产品允许常用音 |
| `的` 的音节 `de` 会命中很多专辑名 | 这是长度 2 的精确全拼，不是模糊。不把阈值抬到 3，否则 `zh` 打不出「周」 |
| 云端不能跑 iOS 测试 | 规则用独立于 Transform 的用例锁住；系统罗马字用例在 Xcode 里跑 |
