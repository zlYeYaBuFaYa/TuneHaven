## 需求 1：快速切歌播错歌（T3）

### 1.1 需求概述
`AudioEngine.load(url:)` 在 `stop()` 之后有两处 `await`（`isPlayable`、`duration`），没有代次校验。A 加载中又加载 B，若 A 的 `isPlayable` 晚于 B 返回，A 会把 `currentItem` 换回 A；`PlaybackService` 只校验 `currentSong`，随后 B 的 `engine.play()` 播出 A，界面显示 B。验收：任意交错下，最后一次 `load` 的文件成为当前 item。

### 1.2 现状分析
`Core/Audio/AudioEngine.swift:48-124`。

### 1.3 技术方案
- 新增 `private var loadGeneration = 0`。`load` 开头 `loadGeneration += 1; let generation = loadGeneration`。
- 每个 `await` 之后 `guard generation == loadGeneration else { return }`：被取代的加载直接返回，不改 `state`、不替换 item、不加时间观察者。
- 新增 `var currentItemURL: URL?`（读 `(player.currentItem?.asset as? AVURLAsset)?.url`），供测试与日志使用。

### 1.4 影响范围
仅 AudioEngine。被取代的加载不再写 `state = .error`。

### 1.5 测试要点
用 `Fixtures/sine-2s.mp3` 复制出 A、B 两个文件，在主 actor 上先启动 `load(A)` 的 Task，`await Task.yield()` 后再启动 `load(B)`（保证 B 是后发起的），两者都结束后 `currentItemURL == B`；重复 20 次。

### 1.6 风险评估
时序依赖真实 AVFoundation，测试为概率性复现；代次校验本身是确定性的，靠代码 Review 保证。

## 需求 2：中断结束无条件恢复（T3）

### 2.1 需求概述
中断结束带 `.shouldResume` 就恢复播放，不管中断前是否在播。用户先暂停、再接电话，挂断后音乐自己响起来。验收：只有中断前在播放才恢复。

### 2.2 现状分析
`AudioEngine.handleInterruption`（245-268）。

### 2.3 技术方案
- 新增 `private var wasPlayingBeforeInterruption = false`。
- `.began`：记录 `wasPlayingBeforeInterruption = isPlaying`，再置 `.paused`。
- `.ended`：`shouldResume && wasPlayingBeforeInterruption` 才恢复；处理后清零。

### 2.4 影响范围
仅 AudioEngine。

### 2.5 测试要点
向 `AudioEngine.shared` 发送 `AVAudioSession.interruptionNotification`（`object` 为 `AVAudioSession.sharedInstance()`）：
1. 暂停状态下 began → ended(shouldResume)：仍为 `.paused`。
2. 播放状态下 began → ended(shouldResume)：恢复为 `.playing`。

### 2.6 风险评估
测试使用共享单例，用例内恢复引擎状态（`stop()`）。

## 需求 3：打开 App 就打断其他 App 音频（T3）

### 3.1 需求概述
`AppDelegate` 启动时对非混音 `.playback` 会话 `setActive(true)`；进后台时 `TuneHavenApp` 再 `ensureActive()`；只加载不播放（`prepare`、自动播放被拦截）时 `loadAndPlay` 与 `AudioEngine.load` 也会激活会话。验收：不开始播放就不激活会话。

### 3.2 现状分析
`App/AppDelegate.swift:38-45`、`App/TuneHavenApp.swift:75-76`、`Core/Audio/AudioSessionManager.swift`、`AudioEngine.load:66-70`、`PlaybackService.loadAndPlay:355`。

### 3.3 技术方案
- `AudioSessionManager` 新增 `configureCategory() -> Bool`：只 `setCategory(.playback)`，不激活，也不改 `isConfigured`。第一次 `ensureActive()` 仍走 `configure()` 完成设置并激活。
- `AppDelegate.configureAudioSession` 改调 `configureCategory()`。
- `TuneHavenApp` 进后台：仅 `playbackService.isPlaying` 时 `ensureActive()`。
- `AudioEngine.load` 删除 `ensureActive` 检查（激活留给 `play()`，`play()` 已有）。
- `PlaybackService.loadAndPlay` 删除开播前的 `audioSession.ensureActive()`（`engine.play()` 内部会激活）。
- 不在暂停时主动停用会话（属另一项改动，不在本次范围）。

### 3.4 影响范围
启动、进后台、预加载三条路径。播放、恢复播放、远程控制播放路径不变（仍经 `AudioEngine.play()` 激活）。

### 3.5 测试要点
`PlaybackService.prepare(song:in:)` 后 `MockAudioSessionManaging.ensureActiveCalled == false`；`play(song:in:)` 后引擎 `playCalled == true`（激活由真实引擎负责，Mock 引擎不涉及）。

### 3.6 风险评估
后台播放依赖播放时会话已激活：开始播放必经 `AudioEngine.play()` → `ensureActive()`，进后台时正在播放仍会再确认一次。

## 需求 4：切歌后歌词串台（T8）

### 4.1 需求概述
`PlayerView` 在歌曲变化时另起 `loadLyrics()`，不取消旧任务也不校验歌曲。上一首在线匹配较慢时，结果会覆盖新歌曲的歌词。验收：只有当前歌曲的加载结果会写入。

### 4.2 现状分析
`Presentation/Player/PlayerView.swift:126`、`176-182`、`484-487`。

### 4.3 技术方案
- `.task { await loadLyrics() }` 改为 `.task(id: playback.currentSong?.id) { await loadLyrics() }`，歌曲变化时 SwiftUI 取消旧任务。
- `onChange(of: currentSong?.id)` 只保留「为 nil 时关闭播放器」，去掉其中的 `Task { await loadLyrics() }`。
- `loadLyrics()`：记录发起时的歌曲 id，`await` 之后 `guard !Task.isCancelled, playback.currentSong?.id == song.id else { return }` 再赋值。其他调用点（歌词编辑后刷新）共用该校验。

### 4.4 影响范围
仅播放页；重做时沿用同一写法。

### 4.5 测试要点
视图层无单测，靠代码 Review；全量回归。

### 4.6 风险评估
无。

## 需求 5：删除／移出当前歌曲时队列与播放不一致（T10、交互 §14）

### 5.1 需求概述
- 从音乐库删除正在播放或在队列中的歌曲，队列与 `currentSong` 不变：迷你播放器仍显示已删歌曲，队列仍列出它。
- 队列页左滑删除直接改数组：移除当前项后高亮跳到下一首，音频仍是原来那首。「清空」后音频继续而队列为空。

验收（已确认「接着放下一首」）：
1. 移除当前项：原来在播放 → 自动播放其后一首；原来暂停 → 切到其后一首并保持暂停；其后没有歌曲 → 停止并清空当前歌曲。
2. 移除非当前项：当前歌曲与播放不受影响，高亮仍正确。
3. 从音乐库删除：队列中对应条目全部移除，按 1、2 处理；当前歌曲不在队列中但被删除时停止并清空。
4. 清空队列：保留当前歌曲作为唯一条目，播放不中断。
5. 撤销删除不把歌曲加回队列。

### 5.2 现状分析
`Domain/Services/PlayQueueService.swift`（`removeFromQueue`、`clearQueue`）、`Presentation/Player/PlayQueueView.swift:72-88`、`Domain/Services/MusicLibraryService.swift:61-69`、`PlaybackService`。

### 5.3 技术方案
- **MusicLibraryService**：新增 `let songsDeleted = PassthroughSubject<Set<UUID>, Never>()`，`softDelete` 成功后发送被删 id。
- **PlaybackService**：
  - `func removeFromQueue(at offsets: IndexSet)`：
    - 记下当前项索引 `idx` 是否在 `offsets` 中、是否正在播放；
    - 若移除当前项：在原队列 `idx` 之后找第一个不在 `offsets` 里的条目作为后继（按队列顺序，不随播放模式随机）；
    - 调 `queue.removeFromQueue(at:)`；
    - 移除了当前项时：有后继 → `queue.advanceToCurrent(后继)`，经无损门禁后 `startLoadAndPlay(song:autoPlay: wasPlaying)`（被拦截则 `parkOnBlockedSong`）；无后继 → `stopAndClearCurrent()`。
  - `func removeSongsFromQueue(ids: Set<UUID>)`：把队列中 id 命中的索引组成 `IndexSet` 调用上面方法；若 `currentSong` 被删但不在队列里，`stopAndClearCurrent()`。
  - `func clearQueue()`：有当前歌曲时 `queue.replaceQueue(with: [current], startAt: 0)`，否则 `queue.clearQueue()`。
  - `private func stopAndClearCurrent()`：`loadTask?.cancel()`、`engine.stop()`、`isPlaying = false`、`currentSong = nil`、`currentCoverPath = nil`、`nowPlaying.clear()`。
  - `setupBindings` 订阅 `libraryService.songsDeleted` → `removeSongsFromQueue(ids:)`。
- **PlayQueueView**：左滑删除与「清空」改调 `playback.removeFromQueue(at:)`、`playback.clearQueue()`。
- `PlayerView` 已有「`currentSong` 为 nil 时关闭播放器」，停止并清空后全屏播放器自动收起。

### 5.4 影响范围
队列编辑、音乐库删除；`PlayQueueService` 本身不改，协调逻辑放在 `PlaybackService`。

### 5.5 测试要点（PlaybackHarness）
1. 播放中移除当前项 → 后一首加载并播放，`queue.currentItem` 为后一首。
2. 暂停中移除当前项 → 后一首加载、未播放。
3. 移除队尾的当前项 → 停止，`currentSong == nil`，Now Playing 被清空。
4. 移除非当前项 → 不加载，`currentSong` 不变，当前索引随之调整。
5. 音乐库删除队列中的非当前歌曲 → 从队列消失。
6. 音乐库删除当前歌曲 → 播放后一首。
7. 清空队列 → 队列只剩当前歌曲，播放未停止。

### 5.6 风险评估
| 风险 | 应对 |
|------|------|
| 后继是无损而用户为 Free | 走与 `playNext` 相同的门禁，停在该首并给软墙信号 |
| 随机模式下用户期望随机下一首 | 移除属于编辑操作，按队列顺序取后继更可预期；随后的自然切歌仍按播放模式 |

## 修改记录

### 2026-11-17：需求 5 改为按交互文档 §7.5 执行

提交 `dd1fc45` 后同步文档时发现，`docs/交互设计文档.md` §7.5 已规定：「清空前说明只清空队列；当前音频继续到结束，之后停止且不自动重建列表。移除当前项时同样不突然切断音频，应标记为队列外播放；下一首从原后继项开始，无后继则停止。」方案阶段只对照了 §14 差异表，遗漏了 §7.5，询问用户时也未提示冲突。用户确认以交互文档为准。

**修订后的需求 5 验收标准**

1. 从队列移除当前项（队列页左滑）：当前音频不中断，进入「队列外播放」（`isPlayingOutsideQueue == true`，队列无高亮）；记住原后继项。当前歌曲播完后从原后继项继续；无后继则停止（与顺序播放到队尾一致，保留当前歌曲在迷你播放器）。
2. 队列外播放期间再移除了原后继项：后继顺延为其后第一个未被移除的条目，没有则为空。
3. 清空队列：队列置空，当前音频继续到结束后停止，不重建列表。
4. 移除非当前项：不变。
5. 音乐库删除（文件已被移走，不能继续播放）：删除的是当前歌曲时立即切到后继项（原来在播放则继续播放，否则保持暂停），无后继则停止并清空当前歌曲；队列外播放的当前歌曲被删时同样处理。
6. 队列外播放期间用户主动播放任意歌曲（点队列、播放其他列表、上一首/下一首），退出队列外状态。

**修订后的技术方案**

- `PlayQueueService` 新增 `detachCurrent()`：`currentIndex = nil`。
- `PlaybackService`：
  - `@Published private(set) var isPlayingOutsideQueue = false`，`private var outOfQueueSuccessorId: UUID?`（QueueItem id）。
  - `removeFromQueue(at:)`（用户编辑）：移除当前项时计算后继 → `queue.removeFromQueue` → `queue.detachCurrent()` → 进入队列外状态，不碰音频。已在队列外状态时，若后继在 `offsets` 中则顺延。
  - `clearQueue()`：`queue.clearQueue()`；有当前歌曲则进入队列外状态、后继为空。
  - `playNext()`：开头若在队列外状态，取出后继并退出该状态：后继存在 → `advanceToCurrent` 后按门禁播放；否则 `stop()`。
  - `loadAndPlay` 开始加载新歌曲时退出队列外状态（覆盖点歌、上一首、其他列表播放）。
  - `removeSongsFromQueue(ids:)`（音乐库删除）：当前项被删 → 立即切后继（`autoPlay = 原播放状态`）或停止并清空；队列外播放的当前歌曲被删 → 同样处理，后继取 `outOfQueueSuccessorId`（若也被删则顺延）。
- 测试按以上 6 条重写需求 5 的用例。
