# 方案：前台恢复纯色页面修复

> 创建日期：2026-03-24 | 状态：Review 通过

## 1. 需求概述

**问题描述**：偶现场景下，从其他应用切换回 TuneHaven，页面变为主题对应的纯色背景，持续存在直到杀进程重启。

**修复目标**：确保 App 在所有生命周期场景下（前后台切换、内存压力回收、热启动等）都不会出现整个页面纯色显示。

**验收标准**：
1. 从任意其他应用切换回 TuneHaven，内容立即可见，无纯色
2. 模拟内存警告后回到 App，页面正常显示
3. 长时间后台（>30 分钟）后回到 App，页面正常显示
4. 在 4 套主题下分别测试，全部正常
5. 从 fullScreenCover/sheet 弹窗状态切后台再回来，正常
6. 不引入新的 UI 闪烁或渲染异常

## 2. 现状分析

### 2.1 视图层级结构

```
UIWindow (backgroundColor = palette.background)
  └─ SwiftUI Hosting Controller
       └─ TuneHavenApp.body
            └─ ZStack
                 ├─ palette.background.ignoresSafeArea()     ← 纯色底层
                 └─ if isReady {
                      RootTabView()                          ← 条件渲染
                        └─ ZStack
                             ├─ ThemeBackgroundView()
                             ├─ LibraryTabView  (opacity 切换)
                             ├─ PlaylistTabView (opacity 切换)
                             └─ SettingsTabView (opacity 切换)
                    }
```

### 2.2 问题代码路径

**路径 A — `.active` 阶段的 `applyToWindows()` (主因)**

```
scenePhase → .active
  → scheduleWindowRefresh(delay: 0.1, fullApply: true)
    → 0.1s 后 applyToWindows()
      → 遍历所有 UIWindow
        → window.backgroundColor = bgColor
        → updateNavigationBars(on: rootViewController, ...)
          → 递归遍历所有 UIViewController
            → nav.view.backgroundColor = bgColor          ← 覆盖 SwiftUI 宿主视图
            → 重建 UINavigationBarAppearance              ← 触发 UIKit 布局
```

问题：在 iOS 恢复 App 前台渲染的关键时刻，`applyToWindows()` 递归修改 UINavigationController 的 `view.backgroundColor` 并重建导航栏外观。这会与 SwiftUI 的渲染管线冲突：
- `nav.view.backgroundColor = bgColor` 使 UINavigationController 的 view 变为不透明纯色
- 如果 SwiftUI hosting view 在 UIKit 布局更新中被置为无效但未能重新渲染，用户看到的就是 UINavigationController 的纯色背景
- 这是一个 UIKit 级别的渲染状态损坏，SwiftUI 不会自动修复，因此持续到杀进程

**技术设计文档明确指出**："前台恢复（scenePhase == .active）时不调用任何窗口刷新，因为 iOS 会保留窗口属性。" 但当前代码与此矛盾。

**路径 B — `isReady` 状态丢失 (辅因)**

```
内存压力 → iOS 回收 App 进程内存
  → SwiftUI 重建视图树
    → @State isReady 重置为 false
      → ZStack 中只剩 palette.background + ProgressView
        → .task { initialize() } 重新执行
          → 如果初始化耗时或失败 → 持续显示纯色
```

问题：`isReady` 通过 `if/else` 条件渲染控制 `RootTabView` 的存在与否。如果 `isReady` 因任何原因为 `false`，整个 `RootTabView` 从视图树中消失，用户看到纯色底层。

**路径 C — `initialize()` 无防重入保护**

如果 `.task` 在某些生命周期场景下被重新触发，`initialize()` 会重复执行 `bootstrap()` / `loadSongs()` 等操作，可能导致意外状态。

### 2.3 受影响文件

| 文件 | 当前问题 |
|------|----------|
| `TuneHaven/App/TuneHavenApp.swift` | `.active` 时调用 fullApply 窗口刷新；`isReady` 条件渲染；`initialize()` 无防重入 |
| `TuneHaven/App/Theme/ThemeManager.swift` | `applyToWindows()` 递归修改 UINavigationController 背景色 |

## 3. 技术方案

### 3.1 整体设计

采用 **4 层防护** 策略，从根源消除、过程防御、状态保护、兜底恢复四个层次确保不出现纯色页面：

```
第 1 层：消除根源 — 移除 .active 时的窗口刷新
第 2 层：过程防御 — applyToWindows() 不再修改 nav.view.backgroundColor
第 3 层：状态保护 — isReady 切换无动画延迟，RootTabView 立即显示
第 4 层：防重入 — initialize() 防止重复执行
```

### 3.2 详细实现

#### Fix 1：移除 `.active` 阶段的窗口刷新（消除根源）

**文件**：`TuneHavenApp.swift`

```swift
// ===== 修改前 =====
.onChange(of: scenePhase) { _, phase in
    AppLogger.shared.debug("[App] scenePhase → \(phase)")
    switch phase {
    case .active:
        container.playbackService.checkSleepTimerOnForeground()
        container.themeManager.scheduleWindowRefresh(delay: 0.1, fullApply: true)  // ← 删除
    case .background:
        container.audioSessionManager.ensureActive()
    default:
        break
    }
}

// ===== 修改后 =====
.onChange(of: scenePhase) { _, phase in
    AppLogger.shared.debug("[App] scenePhase → \(phase)")
    switch phase {
    case .active:
        container.playbackService.checkSleepTimerOnForeground()
        // iOS 保留窗口属性，前台恢复不需要刷新窗口
    case .background:
        container.audioSessionManager.ensureActive()
    default:
        break
    }
}
```

**原理**：iOS 在 App 进入后台时保留所有窗口属性（backgroundColor、UINavigationBarAppearance 等），恢复前台时自动还原，无需手动刷新。主动刷新反而会在 SwiftUI 恢复渲染的关键窗口期触发 UIKit 布局更新，导致渲染冲突。

#### Fix 2：`applyToWindows()` 不再修改 UINavigationController 的 view.backgroundColor（过程防御）

**文件**：`ThemeManager.swift`

```swift
// ===== 修改前 =====
private static func updateNavigationBars(on vc: UIViewController?, bgColor: UIColor, surfaceColor: UIColor) {
    guard let vc = vc else { return }
    if let nav = vc as? UINavigationController {
        nav.view.backgroundColor = bgColor           // ← 危险：覆盖 SwiftUI 宿主视图
        let appearance = UINavigationBarAppearance()
        appearance.configureWithOpaqueBackground()
        appearance.backgroundColor = surfaceColor
        appearance.shadowColor = .clear
        nav.navigationBar.standardAppearance = appearance
        nav.navigationBar.compactAppearance = appearance
        nav.navigationBar.scrollEdgeAppearance = appearance
    }
    // ...递归...
}

// ===== 修改后 =====
private static func updateNavigationBars(on vc: UIViewController?, surfaceColor: UIColor) {
    guard let vc = vc else { return }
    if let nav = vc as? UINavigationController {
        // 不再设置 nav.view.backgroundColor — 由 SwiftUI 的
        // fixNavigationControllerBackground() + NavigationBackgroundFixer 统一管理
        let appearance = UINavigationBarAppearance()
        appearance.configureWithOpaqueBackground()
        appearance.backgroundColor = surfaceColor
        appearance.shadowColor = .clear
        nav.navigationBar.standardAppearance = appearance
        nav.navigationBar.compactAppearance = appearance
        nav.navigationBar.scrollEdgeAppearance = appearance
    }
    for child in vc.children {
        updateNavigationBars(on: child, surfaceColor: surfaceColor)
    }
    if let presented = vc.presentedViewController {
        updateNavigationBars(on: presented, surfaceColor: surfaceColor)
    }
}
```

**原理**：`nav.view.backgroundColor` 的职责已由 SwiftUI 侧的 `NavigationBackgroundFixer` 承担（在 `LibraryTabView` / `PlaylistTabView` / `SettingsTabView` 中通过 `.fixNavigationControllerBackground()` 调用）。`ThemeManager` 不应再重复设置，避免 UIKit 和 SwiftUI 争夺同一属性的控制权。同时 `applyToWindows()` 调用方也需同步去掉 `bgColor` 参数传递。

#### Fix 3：禁止 isReady 切换时的动画延迟（状态保护）

**文件**：`TuneHavenApp.swift`

```swift
// ===== 修改前 =====
ZStack {
    container.themeManager.palette.background
        .ignoresSafeArea()

    if isReady {
        RootTabView()
            .environmentObject(...)
    } else if let error = initError {
        // 错误视图
    } else {
        ProgressView("加载中...")
    }
}

// ===== 修改后 =====
ZStack {
    container.themeManager.palette.background
        .ignoresSafeArea()

    if isReady {
        RootTabView()
            .environmentObject(...)
            .transition(.identity)   // 无动画过渡，立即显示
    } else if let error = initError {
        // 错误视图
    } else {
        ProgressView("加载中...")
    }
}
.animation(nil, value: isReady)  // 禁止 isReady 变化时的所有动画
```

**原理**：
- **保持 `if isReady` 条件渲染不变**：RootTabView 仅在 CoreData 加载完成后创建，避免子视图在 CoreData 未就绪时触发 `.task` / `.onAppear` 导致 fatalError
- **`.transition(.identity)` + `.animation(nil, value: isReady)`**：确保 isReady 从 false → true 时 RootTabView 立即显示，不受任何外层动画影响
- **RootTabView 生命周期稳定**：`isReady` 一旦设为 true 就永远不会回到 false（代码中没有任何路径将其设回 false），因此 RootTabView 一旦创建就不会被条件分支销毁
- **不提前创建 RootTabView 的原因**：子视图（AllSongsView、PlaylistMainView 等）的 `.task` / `.onAppear` 会在 CoreData 加载前触发数据查询，而 `CoreDataStack.backgroundContext` 在 `load()` 前访问会 fatalError

#### Fix 4：`initialize()` 增加防重入保护

**文件**：`TuneHavenApp.swift`

```swift
@State private var isInitializing = false

private func initialize() async {
    guard !isReady && !isInitializing else { return }
    isInitializing = true
    defer { isInitializing = false }

    do {
        AppLogger.shared.info("[App] initialize start")
        try await container.bootstrap()
        try await container.playlistService.initializeSystemPlaylists()
        await container.libraryService.loadSongs()
        await container.libraryService.cleanupOnLaunch()
        container.playbackService.checkSleepTimerOnForeground()
        isReady = true
        AppLogger.shared.info("[App] initialize done — isReady=true")

        if !pendingImportURLs.isEmpty {
            let urls = pendingImportURLs
            pendingImportURLs.removeAll()
            ensureOpenInHandler().enqueue(urls: urls)
        }

        container.themeManager.scheduleWindowRefresh(delay: 0.15, fullApply: true)
    } catch {
        initError = error.localizedDescription
        AppLogger.shared.error("[App] initialize FAILED: \(error)")
    }
}
```

### 3.3 补充：`onAppear` 的窗口刷新保留

```swift
.onAppear {
    AppLogger.shared.debug("[App] onAppear — applying window theme")
    container.themeManager.scheduleWindowRefresh(delay: 0.1, fullApply: true)
}
```

`onAppear` 仅在视图**首次出现**时触发（不会在前后台切换时重复触发），保留此处的窗口刷新是安全的且必要的——确保首次启动时 UIKit 窗口属性正确设置。

## 4. 影响范围

| 受影响模块 | 影响说明 |
|------------|----------|
| App 生命周期 | `.active` 不再触发窗口刷新，由 iOS 自动保留 |
| ThemeManager | `applyToWindows()` 不再修改 nav.view.backgroundColor |
| 导航栏背景 | 全部由 SwiftUI 侧 `NavigationBackgroundFixer` 管理 |
| 主题切换 | `setTheme()` 内部的 `scheduleWindowRefresh` 不受影响 |

数据库：无变更 | 向后兼容：完全兼容

## 6. 风险评估

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 移除 `.active` 窗口刷新后主题切换不生效 | 极低 | 无 - setTheme() 内部有独立刷新 | setTheme() 不受影响 |
| 移除 nav.view.backgroundColor 后转场露白/黑 | 低 | `NavigationBackgroundFixer` 已覆盖此职责 | 回归测试场景 10 验证 |
| `onAppear` 在某些 iOS 版本多次触发 | 极低 | 多次执行 `scheduleWindowRefresh`，但有防抖机制（pendingRefreshTask.cancel） | 已有 Task cancel 防抖 |
