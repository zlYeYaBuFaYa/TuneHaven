# 方案：WiFi 串行导入（Review T5，含 T1/T5 两个关联中危项）

> 创建日期：2026-11-17 | 状态：草稿

## 1. 需求概述

WiFi 传输时网页逐个上传文件，服务端收到一个就回 200，网页紧接着传下一个。`WiFiTransferView` 为每个文件各起一个 `processWiFiFile` Task，而导入入口受 `BackupActivityGate` 互斥：前一首还在哈希、解析时，后一首拿不到闸门直接失败。App 内「已接收」列表对每个文件都显示绿色对勾，网页也显示上传成功，用户无从得知歌曲丢失。

一并修复两个关联中危项：

- **同名覆盖（T1）**：上传文件按原名写入 `tmp/wifi_upload/`。排队后，第二个同名文件（如不同专辑的 `01.mp3`）会在第一个导入前覆盖它。
- **临时文件不删（T5）**：导入使用复制，`wifi_upload/` 里的上传文件永不删除，每首歌占两份空间；启动清理只清 tmp 根目录下 `wifi_upload_` 前缀的文件，匹配不到该子目录。

验收标准：

1. 连续上传 N 个文件，全部按到达顺序逐个导入，不因闸门冲突失败。
2. 备份等任务占用闸门时，队列等待其结束后继续，不判失败。
3. 同名文件分别落盘、分别导入。
4. 每个文件处理完（无论成功与否）删除其上传临时文件；启动时清空 `wifi_upload/`。
5. App 内列表按真实结果显示：等待中 / 导入中 / 已导入 / 已存在 / 失败（附原因）。
6. 关闭 WiFi 传输页后，已收到但尚未导入的文件继续导入完成。

## 2. 现状分析

| 文件 | 现状 |
|------|------|
| `Core/Network/WiFiTransferServer.swift` `parseMultipart` | `destURL = wifiUploadURL/原文件名`，同名覆盖 |
| `WiFiTransferServer.cleanupTempFiles()` | 只删 tmp 根目录 `wifi_upload_` 前缀文件（流式上传的中间文件） |
| `Presentation/Import/WiFiTransferView.swift` `tryStart` | 每个文件一个 Task 直接调 `processWiFiFile`；`receivedFiles` 只记文件名，统一显示对勾 |
| `Domain/Services/ImportService.swift` `processWiFiFile` | 先 `beginExternalImport()`，忙则返回 `.failed`；复制入库，不删源文件 |
| `Domain/Services/BackupActivityGate.swift` | 无查询忙碌状态的接口 |
| `OpenInImportHandler` | 也调用 `processWiFiFile`，传入的是外部文件 URL，**不能**由导入方删除源文件 |

## 3. 技术方案

### 3.1 整体设计

```
WiFiTransferServer ──onFileReceived(原名, 唯一临时 URL)──▶ WiFiImportQueue.enqueue
                                                          │ 串行 Task（持有自身直到排空）
                                                          ▼
                              importer.isImportBusy ? 等待 retryInterval 后再查
                                                          ▼
                              importer.processWiFiFile → 更新条目状态 → 删除临时文件
                                                          ▼
                              队列排空且本轮有成功 → onImported()（刷新曲库）
```

### 3.2 详细实现

**Domain/Repositories/WiFiFileImporting.swift（新）**

```swift
@MainActor
protocol WiFiFileImporting: AnyObject {
    /// 导入或备份正在进行，此时调用导入会被拒绝
    var isImportBusy: Bool { get }
    func processWiFiFile(tempURL: URL, originalFilename: String) async -> SingleImportResult
}
```

`ImportService` 已是 `@MainActor`，用 extension 遵循；`isImportBusy` 读 `activityGate?.isBusy ?? false`。

**BackupActivityGate**：新增 `var isBusy: Bool`（加锁读 `backupBusy || importBusy`）。

**Domain/Services/WiFiImportQueue.swift（新，@MainActor ObservableObject）**

- `struct Item: Identifiable { id, fileName, status }`；`enum Status: Equatable { waiting, importing, imported, duplicate, failed(String) }`。
- `@Published private(set) var items: [Item]`。
- `init(retryInterval: Duration = .seconds(1), removeFile: @escaping (URL) -> Void = { try? FileManager.default.removeItem(at: $0) })`。
- `configure(importer: WiFiFileImporting, onImported: @escaping @MainActor () async -> Void)`：视图拿到环境对象后调用。
- `enqueue(fileURL:originalFilename:)`：追加 `.waiting` 条目和待处理记录；没有运行中的处理 Task 时启动一个。
- 处理 Task：`Task { await self.drain() }`，强引用 self，排空前不释放（满足验收 6）。
- `drain()`：循环取第一个待处理项：
  - 未配置 importer → 该项 `.failed("导入服务未就绪")`，删除临时文件；
  - `while importer.isImportBusy { try? await Task.sleep(for: retryInterval) }`；
  - 状态置 `.importing` → `await importer.processWiFiFile` → 映射结果；
  - `removeFile(tempURL)`；
  - 处理期间新入队的文件在同一个循环里继续处理；队列真正排空时，若自上次回调以来有 `.imported`，`await onImported()` 一次。
- 结果映射：`success`、`successIncompleteMetadata` → `.imported`；`skippedDuplicate` → `.duplicate`；其余 → `.failed(errorMessage ?? "导入失败")`。
- `@MainActor` 下「检查忙碌 → 调用 `processWiFiFile`」之间没有挂起点（同 actor 的 async 调用同步进入，`beginExternalImport` 在第一个 `await` 前执行），不会被其他任务插入。

**WiFiTransferServer**

- 新增 `static func uploadDestination(for rawFilename: String, in directory: URL) -> URL`：取 `lastPathComponent`，空串、`.`、`..` 退回 `uploaded_file`，最终名为 `"\(UUID().uuidString)-\(name)"`。
- `parseMultipart` 改用它；`savedFiles` 中 `name` 仍为原文件名（作为 `originalFilename` 传给导入）。
- `cleanupTempFiles()` 额外清空 `SandboxPathManager.wifiUploadURL` 目录内容（启动时 `bootstrap` 已调用，此时队列为空）。

**WiFiTransferView**

- 删除 `ReceivedFile`、`receivedFiles`；新增 `@StateObject private var importQueue = WiFiImportQueue()`。
- `tryStart`：`importQueue.configure(importer: importService, onImported: { await libraryService.loadSongs() })`；`server.onFileReceived = { name, url in importQueue.enqueue(fileURL: url, originalFilename: name) }`。
- 列表按 `importQueue.items` 显示状态图标与说明，颜色取 `palette` / `SemanticColor`；标题改为「已接收 N 个文件」，失败条目显示原因。
- `onDisappear` 不再清空列表（视图销毁时队列条目随之不可见，但处理 Task 继续）。

### 3.3 备选方案

服务端等导入完成再回包：网页天然串行、可显示真实结果，但需改造服务器回调为异步并长时间挂起连接，改动更大。已确认采用队列方案。

## 4. 影响范围

- `OpenInImportHandler` 不变（仍直接调 `processWiFiFile`，不删外部源文件）。
- 网页行为不变。
- 无数据模型变更；新增两个 Domain 文件。

## 5. 测试要点

新增 `TuneHavenTests/WiFiImportQueueTests.swift`（Mock importer，`retryInterval` 设为毫秒级）：

1. 连续入队 3 个文件：按顺序处理，任一时刻最多 1 个在导入（Mock 记录并发峰值）。
2. 结果映射：成功 / 元数据不全 / 重复 / 失败分别得到对应状态，失败带原因。
3. 每个文件处理后都调用 `removeFile`（含失败、重复）。
4. importer 忙时等待，忙碌解除后继续导入，不判失败。
5. 排空后 `onImported` 只调用一次；全部重复/失败时不调用。
6. 未配置 importer 时条目失败且删除临时文件。

`WiFiTransferSessionTests` 补充：

7. `uploadDestination`：同名两次得到不同 URL，均在目标目录内，保留原文件名作后缀；`../x.mp3` 只取 `x.mp3`；`..`、空串退回 `uploaded_file`。
8. `cleanupTempFiles()` 清空 `wifi_upload/` 下的文件。

回归：全量 `TuneHavenTests`。

## 6. 风险评估

| 风险 | 应对 |
|------|------|
| 备份长时间占用闸门，队列一直等待 | 每秒检查一次，开销可忽略；条目显示「等待中」 |
| 关闭页面后重新打开，新旧两个队列同时存在 | 两者都先查闸门，最多一个在导入，另一个等待 |
| 未配置即入队 | `tryStart` 先 `configure` 再启动服务；兜底按失败处理并删临时文件 |
| 测试中 `cleanupTempFiles` 清理测试宿主 tmp | 宿主无用户数据，可接受 |
| WiFi 队列导入期间「从其他 App 打开」文件 | `OpenInImportHandler` 仍会因闸门忙而提示失败，行为与修复前一致，不在本次范围（T9） |
