# 方案：封面存储迁移（Review T11）

> 创建日期：2026-11-17 | 状态：已完成

## 1. 需求概述

歌曲封面和歌单封面目前只存在 `Library/Caches/CoverImages`、`Library/Caches/PlaylistCovers`。设置页「清理封面缓存」和 `ImageCacheManager` 的 LRU 淘汰会删掉这两个目录里的文件，系统空间不足时也可能清理 Caches。Apple Music 导入封面、分享收到的封面、用户自选的歌单封面删除后无法恢复。

目标：

1. 封面的正式存储迁到 `Library/Application Support/CoverImages`、`Library/Application Support/PlaylistCovers`，不再被用户操作或系统清理删除。
2. 升级用户首次启动时，把旧 Caches 目录中的封面一次性迁移到新目录，迁移可重入、失败不阻塞启动。
3. `ImageCacheManager` 只负责内存缓存，磁盘读写只读正式目录；不再有磁盘 LRU 淘汰，也不再提供「清理」能力。
4. 设置页去掉「最大缓存限制」和「清理封面缓存」，保留只读的「封面占用」。
5. 顺带修复：自定义歌单封面写入 `PlaylistCovers` 后，`CoverImageView` 按 key 只在 `CoverImages` 里找，导致自定义封面不显示（或显示旧的拼图缓存）。

验收标准：

- 任何设置操作都不会删除封面文件；超过原 100MB 上限也不会淘汰。
- 升级后已有歌曲封面、自动拼图封面、自定义歌单封面全部正常显示。
- 设置自定义歌单封面后立即显示新图。
- 备份导出/恢复、分享发送/接收的封面读写路径跟随新目录。

## 2. 现状分析

| 文件 | 现状 |
|------|------|
| `Core/Storage/SandboxPathManager.swift` | `coverImagesURL`、`playlistCoversURL` 指向 `Caches` |
| `Core/Cache/ImageCacheManager.swift` | `store` 把 JPEG 再写一份到 `CoverImages/{key}`；`clearAll` 清空两个目录；`evictIfNeeded` 按修改时间删除两个目录的文件；`imageAsync` 只读 `CoverImages/{key}` |
| `App/CoverImageProcessor.swift` | 歌曲封面写 `CoverImages/{id}_medium.jpg` 后 `store`；拼图写 `PlaylistCovers/{id}.jpg` 后 `store`（因此 `CoverImages` 里多一份同名副本）；自定义歌单封面写 `PlaylistCovers/{id}.jpg`，不 `store` |
| `Domain/Repositories/ImageCacheManaging.swift` | 协议含 `setCacheLimit`、`clearAll` |
| `Presentation/Settings/SettingsStorageSection.swift`、`SettingsView.swift` | 缓存占用、上限滑块、清理按钮；`@AppStorage(cache_limit_mb)` |
| `App/AppStorageKey.swift` | `cacheLimitMB` |
| `Core/Persistence/MigrationManager.swift` | 版本升级任务，无文件迁移 |
| `App/AppDIContainer.swift` `bootstrap()` | 先 `runVersionUpgradeTasks`、Core Data，后 `createAllDirectories` |
| 备份 `BackupFileLayout.coverDirectory`、`ShareService`、`FileStorageService.coverImagesDirectoryURL` | 都经 `SandboxPathManager.coverImagesURL` 取路径，改路径后自动跟随 |

## 3. 技术方案

### 3.1 整体设计

```
SandboxPathManager
  applicationSupportURL           新增
  coverImagesURL / playlistCoversURL   → Application Support 下
  legacyCoverImagesURL / legacyPlaylistCoversURL   → Caches 下（只供迁移）

CoverStorageMigration（Core/Storage，新增）
  migrate(legacyCovers:legacyPlaylistCovers:covers:playlistCovers:fileManager:) -> Result

AppDIContainer.bootstrap()
  createAllDirectories() 之后、任何界面读取之前执行迁移

ImageCacheManager（只做内存缓存 + 读正式目录）
  imageAsync(key): 内存 → PlaylistCovers/{key} → CoverImages/{key}
  store(image,key): 只写内存 + 发通知
  cacheSizeAsync(): 统计两个正式目录大小
```

### 3.2 详细实现

**SandboxPathManager**

- 新增 `applicationSupportURL`（`.applicationSupportDirectory`）。
- `coverImagesURL = applicationSupportURL/CoverImages`，`playlistCoversURL = applicationSupportURL/PlaylistCovers`。
- 新增 `legacyCoverImagesURL = cachesURL/CoverImages`、`legacyPlaylistCoversURL = cachesURL/PlaylistCovers`。
- `createAllDirectories` 不变（列表已包含两个封面目录，会在 Application Support 下创建，`withIntermediateDirectories: true` 同时建好 Application Support 本身）。

**CoverStorageMigration（新文件 `Core/Storage/CoverStorageMigration.swift`）**

```swift
enum CoverStorageMigration {
    struct Result: Equatable { var moved = 0; var skipped = 0; var failed = 0 }

    static func migrate(legacyCovers:, legacyPlaylistCovers:, covers:, playlistCovers:, fileManager: = .default) -> Result
}
```

规则：

1. 旧目录不存在 → 直接返回（已迁移或新装用户）。
2. 先迁 `legacyPlaylistCovers` → `playlistCovers`，再迁 `legacyCovers` → `covers`。
3. `legacyCovers` 中与歌单封面同名的文件是拼图封面的缓存副本，删除不迁（计入 skipped）。「歌单封面名」取迁移开始时 `legacyPlaylistCovers` 与 `playlistCovers` 两个目录文件名的并集，这样上次迁移中途退出、旧歌单目录已删除时仍能识别副本。
4. 目标已存在同名文件 → 保留目标、删除旧文件（skipped）。
5. `moveItem` 失败 → 记 failed、保留旧文件，不删旧目录，下次启动重试。
6. 某个旧目录全部处理且无 failed → 删除该旧目录。
7. 失败只写 `ErrorLogger`，不抛出，不阻塞启动。

同卷 `moveItem` 只是重命名，几千个文件在毫秒到百毫秒级，可以在 `bootstrap` 里同步执行。

**AppDIContainer.bootstrap()**

在 `SandboxPathManager.createAllDirectories()` 之后调用 `CoverStorageMigration.migrate(...)` 并记录 info 日志。`bootstrap` 完成前界面不显示，因此不存在迁移中途读取封面的情况。

**ImageCacheManager**

- 删除 `cacheLimitLock`、`trackedCacheSize`、`setCacheLimit`、`evictIfNeeded`、`clearAll`、`cacheFileURL`。
- 新增 `init(coverDirectory: URL, playlistCoverDirectory: URL)`（internal，供测试注入临时目录）；`shared` 使用 `SandboxPathManager` 的两个目录。
- `fileURL(forKey:)`：对 key 做现有的清洗（去 `..`、`/`、`\`），依次查 `playlistCoverDirectory/key`、`coverDirectory/key`，返回第一个存在的；都不存在返回 nil。
- `imageAsync` 改用 `fileURL(forKey:)`；已废弃且无调用方的同步 `image(forKey:)`、`cacheSize()`、`formattedCacheSize()`，以及与协议扩展 `formattedCacheSize() async` 重复且无调用方的 `formattedCacheSizeAsync()` 一并删除。
- `store`：只写内存缓存 + 主线程发 `.imageCacheDidUpdate`，不写磁盘（磁盘文件由 `CoverImageProcessor` 负责）。
- `cacheSizeAsync`：在 `fileQueue` 上统计两个正式目录；设置页继续通过协议扩展 `formattedCacheSize()` 显示。

**ImageCacheManaging 协议与 Mock**

删除 `setCacheLimit`、`clearAll`；`MockImageCacheManaging` 同步删除对应成员。

**CoverImageProcessor.processPlaylistCover**

写盘成功后 `await MainActor.run { imageCache.store(image: thumb, forKey: url.lastPathComponent) }`，让内存缓存替换为新图并通知界面刷新。

**设置页**

- `SettingsStorageSection`：删除 `cacheLimitMB`、`showClearCacheConfirm` 绑定与 `cacheLimitRow`、`clearCacheRow`；`cacheSizeRow` 文案改为「封面占用」。
- `SettingsView`：删除 `@AppStorage(cacheLimitMB)`、`showClearCacheConfirm` 状态及传参。
- `AppStorageKey.cacheLimitMB` 删除。已写入 UserDefaults 的旧值不再读取，不影响任何逻辑。

### 3.3 备选方案

| 方案 | 结论 |
|------|------|
| 目录不动，只让清理/淘汰不删文件 | 系统清理 Caches 的风险仍在，不采用 |
| 正式目录 + 独立磁盘缓存目录 | 目前没有可重建的派生图，额外的磁盘缓存没有收益，不采用 |

## 4. 影响范围

- 存储位置变化：Application Support 参与 iCloud/电脑备份（封面体积小，每首约 20–40KB），符合用户数据定位。
- 备份、分享的封面目录随 `SandboxPathManager` 自动切换，无代码改动。
- 无 Core Data 变更；Core Data 只存文件名，迁移不改数据库。
- 设置页少两行；`cache_limit_mb` 偏好废弃。
- 内存缓存行为不变（50MB、内存警告清空）。

## 5. 测试要点

新增 `TuneHavenTests/CoverStorageTests.swift`（临时目录注入）：

1. 迁移：旧目录有歌曲封面和歌单封面 → 移到新目录，旧目录被删除。
2. 迁移：旧 CoverImages 中与 PlaylistCovers 同名的副本被丢弃，不出现在新 CoverImages。
3. 迁移：目标已存在同名文件 → 保留目标内容，旧文件删除。
4. 迁移：旧目录不存在 → 无操作，返回全 0。
5. 迁移：重复执行（幂等）结果一致。
6. `ImageCacheManager.imageAsync`：key 只在 PlaylistCovers → 能读到；只在 CoverImages → 能读到；都没有 → nil。
7. `store` 不在磁盘写任何文件。
8. `cacheSizeAsync` 统计两个目录之和。
9. 已有 `FileStorageServiceTests` 路径测试：断言改为位于 Application Support 下。

回归：全量 `TuneHavenTests`。

## 6. 风险评估

| 风险 | 应对 |
|------|------|
| 迁移中途被杀进程 | 每个文件独立 move，已移动的不会重复；未完成的下次启动继续 |
| 旧目录已被系统清理 | 旧封面本就丢失，迁移无操作；与修复前一致，不会更差 |
| 第三方路径硬编码 Caches | 已全局搜索，所有读写都经 `SandboxPathManager` |
| 设置页移除选项引起用户疑问 | 只读占用仍保留；需求文档同步说明 |
