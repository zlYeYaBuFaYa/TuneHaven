## 需求 1：P0 — PlaybackService Task 竞态修复（🔴 阻塞级）

### 1.1 需求概述

修复 `PlaybackService` 中 `togglePlayPause()`、`playNext()`、`playPrevious()` 三个方法创建未跟踪 `Task` 导致的竞态条件。快速连续操作时，多个 `loadAndPlay` Task 可交错执行，造成 `currentSong` 与实际播放内容不一致。同时修复 `loadAndPlay` 中 `await engine.load(url:)` 后未检查歌曲是否过期的问题（C2）。

### 1.2 现状分析

**相关文件：**
- `Domain/Services/PlaybackService.swift`

**现状：**
- L109：`togglePlayPause()` → `Task { await loadAndPlay(song: song) }`
- L124：`playNext()` → `Task { await loadAndPlay(song: nextItem.song) }`
- L136：`playPrevious()` → `Task { await loadAndPlay(song: prevItem.song) }`
- L275-295：`loadAndPlay` 在 L290 设置 `currentSong = song`，L295 `await engine.load(url:)` 挂起后未检查歌曲是否仍为期望歌曲
- L74-84：`play(song:in:)` 未显式处理 `.error` 状态（C1，代码清晰度）

### 1.3 技术方案

**1. 引入 loadTask 跟踪机制**

```swift
// PlaybackService.swift
private var loadTask: Task<Void, Never>?

private func startLoadAndPlay(song: Song, autoPlay: Bool = true) {
    loadTask?.cancel()
    loadTask = Task {
        await loadAndPlay(song: song, autoPlay: autoPlay)
    }
}
```

将 `togglePlayPause()`、`playNext()`、`playPrevious()` 中的 `Task { await loadAndPlay(...) }` 全部替换为 `startLoadAndPlay(song:)`。

**2. loadAndPlay 内增加取消检查和过期检查**

```swift
private func loadAndPlay(song: Song, autoPlay: Bool = true) async {
    currentSong = song
    preferences.lastPlayedSongId = song.id.uuidString
    audioSession.ensureActive()
    
    await engine.load(url: fileURL)
    
    // 取消检查
    guard !Task.isCancelled else { return }
    // 过期检查：挂起期间可能已切换到其他歌曲
    guard currentSong?.id == song.id else { return }
    
    applySpeedForSong(song)
    if autoPlay {
        engine.play()
        isPlaying = true
        // ...
    }
}
```

**3. play(song:in:) 补充 .error 状态显式处理（C1）**

```swift
func play(song: Song, in context: PlayContext) async {
    if song.id == currentSong?.id {
        if case .playing = engine.state { return }
        if case .paused = engine.state {
            audioSession.ensureActive()
            engine.play()
            isPlaying = true
            return
        }
        // .error / .idle / .loading → fallthrough 到重新加载
    }
    // ... buildQueue + startLoadAndPlay
}
```

### 1.4 影响范围

| 范围 | 说明 |
|------|------|
| 受影响方法 | `togglePlayPause`, `playNext`, `playPrevious`, `play(song:in:)`, `loadAndPlay`, `prepare(song:in:)` |
| 受影响文件 | 仅 `PlaybackService.swift`（1 个文件） |
| 向后兼容 | ✅ 外部 API 不变 |

### 1.5 测试要点

| 场景 | 验证内容 |
|------|---------|
| 快速连续 playNext | 最终播放歌曲与 currentSong 一致 |
| playNext 后立即 playPrevious | 前一个 Task 被取消，最终播放 previous 歌曲 |
| loadAndPlay 期间 Task.isCancelled | 不执行 engine.play()，不更新 UI 状态 |
| engine.state == .error 时同首歌重播 | 正确走 buildQueue + loadAndPlay |
| 正常播放/暂停/切歌 | 无回归 |

### 1.6 风险评估

| 风险 | 等级 | 应对 |
|------|------|------|
| cancel 后旧 Task 仍短暂执行 | 低 | `Task.isCancelled` 检查兜底 |
| prepare() 与 play() 并发调用 | 低 | prepare 也需使用 loadTask 跟踪 |

## 需求 2：P1 — 用户体验影响修复（3 项 🟡）

### 2.1 需求概述

修复 3 个直接影响用户可见行为的 🟡 级问题：
1. **H1/H2**：歌单歌曲计数包含已软删除歌曲，显示偏高
2. **G1**：WebDAVAccountStore `deleteAccount` 使用 `queue.async`，非原子操作
3. **D1**：ImportService 静默吞噬封面处理错误

### 2.2 现状分析

**相关文件：**
- `Data/Repositories/CoreDataPlaylistRepository.swift`（H1）
- `Data/Repositories/CoreDataPlaylistGroupRepository.swift`（H2）
- `Data/WebDAVAccountStore.swift`（G1）
- `Domain/Services/ImportService.swift`（D1）

**H1 现状**（CoreDataPlaylistRepository.swift L326-350）：
`batchSongCounts` 聚合查询直接对 `PlaylistSongEntity` 计数，未 JOIN `SongEntity` 过滤 `softDeleted == NO`。

**H2 现状**（CoreDataPlaylistGroupRepository.swift L154-175）：
`batchPlaylistSongCounts` 同样未排除 softDeleted 歌曲关联。

**G1 现状**（WebDAVAccountStore.swift L40-52）：
`deleteAccount` 使用 `queue.async`（fire-and-forget），而 `saveAccount` 使用 `queue.sync`，策略不一致。密码删除和账户删除非原子操作。

**D1 现状**（ImportService.swift L160-161）：
`try? await coverProcessor.processSongCover(...)` 用 `try?` 静默吞噬错误，歌曲入库但无封面，用户不可知。

### 2.3 技术方案

**H1/H2：batchSongCounts 过滤 softDeleted**

方案：聚合查询增加 SUBQUERY 条件，排除 songId 对应的 SongEntity.softDeleted == true 的关联。

```swift
// CoreDataPlaylistRepository.swift - batchSongCounts
let countReq: NSFetchRequest<NSDictionary> = NSFetchRequest(entityName: "PlaylistSongEntity")
// 增加：排除 softDeleted 歌曲
let notDeleted = NSPredicate(
    format: "SUBQUERY(SELF, $x, $x.songId == songId AND SUBQUERY(%@, $s, $s.id == $x.songId AND $s.softDeleted == YES).@count > 0).@count == 0",
    ...
)
```

实际实现方式：由于 `PlaylistSongEntity` 与 `SongEntity` 无直接 CoreData 关系，需用两步查询：
1. 先查出所有 softDeleted songId 集合
2. 在聚合查询中添加 `NOT (songId IN %@)` 谓词

```swift
// 步骤1：获取所有 softDeleted 的 songId
let deletedReq = SongEntity.fetchRequest()
deletedReq.predicate = NSPredicate(format: "softDeleted == YES")
deletedReq.propertiesToFetch = ["id"]
let deletedIds = try ctx.fetch(deletedReq).compactMap { $0.id }

// 步骤2：聚合时排除
if !deletedIds.isEmpty {
    countReq.predicate = NSPredicate(format: "NOT (songId IN %@)", deletedIds as NSArray)
}
```

`CoreDataPlaylistGroupRepository.batchPlaylistSongCounts` 同理处理。

**G1：WebDAVAccountStore deleteAccount 同步化**

将 `deleteAccount` 从 `queue.async` 改为 `queue.sync`，确保方法返回时操作已完成：

```swift
func deleteAccount(id: UUID) {
    queue.sync { [self] in     // async → sync
        var accounts = _loadAccounts()
        accounts.removeAll { $0.id == id }
        // Keychain 和 UserDefaults 操作在同一同步块内完成
        KeychainHelper.deleteString(forKey: "webdav_password_\(id.uuidString)")
        do {
            let data = try JSONEncoder().encode(accounts)
            UserDefaults.standard.set(data, forKey: accountsKey)
        } catch {
            ErrorLogger.shared.log(.databaseError(error), context: "deleteAccount: 编码失败")
        }
    }
}
```

**D1：ImportService 封面错误传播**

将 `try?` 改为 `try`，封面处理失败时记录日志但不阻断导入。返回 `SingleImportResult` 增加封面失败标记：

```swift
do {
    coverImagePath = try await coverProcessor.processSongCover(data: coverData, songId: songId)
} catch {
    log.error(error, context: "封面处理失败: \(songId)")
    // 歌曲仍然入库，但标记封面处理失败
}
```

状态改为 `.successIncompleteMetadata`（复用现有状态），在导入结果摘要中提示用户。


> 子批次 D 先于 A 执行，因为 A7（ShareService 去 UIKit 依赖）需要子批次 D 中定义的 `BackgroundTaskProviding` 协议和实现。

每个批次/子批次独立编码、独立测试、独立 commit。
