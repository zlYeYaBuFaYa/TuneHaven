# 方案：歌曲与歌单同步/导出

> 创建日期：2026-03-29 | 状态：已审核（Review 2 轮通过）

## 1. 需求概述

为 TuneHaven 新增歌曲与歌单的**导出/同步**功能，支持在不同 iOS 设备之间传输音乐和歌单数据。

### 1.1 功能范围

| 操作对象 | 支持通道 | 操作粒度 |
|----------|---------|---------|
| 歌曲（音频+封面+歌词+元数据） | WiFi 局域网 / 文件导出导入 | 单个 / 批量 / 全量 |
| 自建歌单（结构+可选音频） | WiFi 局域网 / 文件导出导入 | 单个 / 批量 / 全量 |

- 系统歌单（我喜欢/最近播放）不支持导出
- 不涉及 iCloud
- 同步/导出为基础功能，不受订阅限制

### 1.2 核心规则

| 规则 | 描述 |
|------|------|
| 歌曲匹配 | 主匹配：标题+艺术家+专辑+时长；兜底：标题+艺术家 |
| 歌单冲突 | 弹窗选择：替换 / 合并（存在跳过，不存在新增） / 新建副本 |
| 歌曲冲突 | 弹窗选择：替换 / 跳过 / 另存副本 |
| 批量冲突 | 提供「应用到全部」选项 |
| 缺失歌曲 | 歌单中保留，灰色标记「未找到」，播放时跳过，导入对应文件后自动恢复 |
| 附属资源 | 歌曲导出时一并导出封面和歌词文件 |
| 用户行为 | 不同步 playCount、isFavorite、lastPlayedDate 等 |
| 歌单分组 | 导出时携带分组信息，导入时分组不存在则自动创建 |
| 传输保护 | WiFi 传输支持智能跳过（已完成的文件不重传） |
| 导出预估 | 导出前显示预估文件大小 |

### 1.3 入口

设置 → **同步与传输**（整合现有「导入音乐」+ 新增「导出」功能）

#### 3.2.1 同步类型定义（`Domain/Entities/SyncTypes.swift`）

```swift
// 导出内容类型
enum SyncContentType: String, Codable {
    case songs = "songs"
    case playlists = "playlists"
    case playlistsWithAudio = "playlists_with_audio"
}

// 歌曲导出元数据（不含用户行为数据）
struct SongExportData: Codable {
    let title: String
    let artist: String
    let album: String
    let duration: TimeInterval
    let format: String
    let sampleRate: Int?
    let bitRate: Int?
    let channels: Int?
    let trackNumber: Int?
    let year: Int?
    let genre: String?
    let audioFileName: String      // 音频文件相对路径
    let coverFileName: String?     // 封面文件相对路径
    let lyricsFileName: String?    // 歌词文件相对路径
}

// 歌单导出数据
struct PlaylistExportData: Codable {
    let name: String
    let description: String?
    let groupName: String?         // 所属分组名称（用名称而非 ID，跨设备无法对齐 UUID）
    let coverFileName: String?     // 歌单封面文件相对路径
    let songs: [SongExportData]    // 歌单内歌曲引用
    let sortOrder: Int
}

// .tunehaven 包清单
struct TuneHavenManifest: Codable {
    let version: Int = 1
    let exportDate: Date
    let contentType: SyncContentType
    let deviceName: String
    let songs: [SongExportData]?
    let playlists: [PlaylistExportData]?
}

// 歌曲匹配结果
enum SongMatchResult {
    case exactMatch(Song)          // 四项全匹配
    case fuzzyMatch(Song)          // 标题+艺术家匹配
    case noMatch                   // 未找到
}

// 冲突处理选择
enum SongConflictResolution {
    case replace       // 替换本地
    case skip          // 跳过
    case saveAsCopy    // 另存为副本
}

enum PlaylistConflictResolution {
    case replace       // 替换本地歌单
    case merge         // 合并（存在跳过，不存在新增）
    case createCopy    // 新建副本
}

// 冲突信息
struct SongConflict {
    let incoming: SongExportData
    let existing: Song
    var resolution: SongConflictResolution?
}

struct PlaylistConflict {
    let incoming: PlaylistExportData
    let existing: Playlist
    var resolution: PlaylistConflictResolution?
}

// 同步进度
struct SyncProgress {
    let phase: SyncPhase
    let current: Int
    let total: Int
    let currentFileName: String?
}

enum SyncPhase {
    case preparing       // 准备中
    case exporting       // 导出打包中
    case transferring    // 传输中
    case importing       // 导入解析中
    case matching        // 歌曲匹配中
    case completed       // 完成
    case failed(String)  // 失败
}

// 导入结果
struct SyncImportResult {
    let songsImported: Int
    let songsSkipped: Int
    let songsFailed: Int
    let playlistsImported: Int
    let playlistsSkipped: Int
    let missingSongsCount: Int     // 歌单中缺失的歌曲数
}

// 缺失歌曲引用（存储在 CoreData 中，用于后续自动恢复）
struct MissingSongReference: Codable {
    let title: String
    let artist: String
    let album: String
    let duration: TimeInterval
    let playlistId: UUID           // 所属歌单
}
```

#### 3.2.3 `.tunehaven` 文件格式

`.tunehaven` 本质是 ZIP 压缩包，内部结构：

```
package.tunehaven (ZIP)
├── manifest.json                  # TuneHavenManifest JSON
├── playlists/                     # 歌单封面（如有）
│   └── cover_0.jpg
├── songs/                         # 音频文件（如有），序号前缀避免重名
│   ├── 0001_晴天-周杰伦.mp3
│   ├── 0002_01.mp3
│   └── ...
├── covers/                        # 歌曲封面文件（如有）
│   ├── 0001_cover.jpg
│   └── ...
└── lyrics/                        # 歌词文件（如有）
    ├── 0001_晴天-周杰伦.lrc
    └── ...
```

**文件名唯一性**：打包时为每首歌分配序号前缀（`0001_`、`0002_`...），`SongExportData.audioFileName` 存储包内带前缀的路径，避免不同专辑的同名文件冲突。

**批量歌曲导出**：批量导出歌曲也打包为 `.tunehaven` 文件（`contentType = .songs`），保持与歌单导出一致的分享体验。

实现要点：
- 使用系统 `FileManager` + `Data` 进行 ZIP 压缩/解压（或引入轻量 ZIP 库）
- 打包在后台线程执行，通过 progressHandler 报告进度
- 解包到 `SandboxPathManager.importTempURL` 临时目录，导入完成后清理

#### 3.2.6 歌曲匹配引擎

```swift
// 在 SyncImportService 内部

// 在 analyze() 阶段一次性加载并构建索引，避免每首歌都 fetchAll
private var songIndex: [String: [Song]] = [:]  // key = "title|artist"

private func buildSongIndex() async {
    let allSongs = await songRepo.fetchAll()
    songIndex = Dictionary(grouping: allSongs) { "\($0.title)|\($0.artist)" }
}

private func matchSong(_ exportData: SongExportData) -> SongMatchResult {
    let key = "\(exportData.title)|\(exportData.artist)"
    guard let candidates = songIndex[key] else { return .noMatch }

    // 精确匹配：标题 + 艺术家 + 专辑 + 时长（±2秒容差）
    if let exact = candidates.first(where: {
        $0.album == exportData.album &&
        abs($0.duration - exportData.duration) < 2.0
    }) {
        return .exactMatch(exact)
    }

    // 兜底匹配：标题 + 艺术家（已通过 key 匹配）
    if let fuzzy = candidates.first {
        return .fuzzyMatch(fuzzy)
    }

    return .noMatch
}
```

**性能优化**：`analyze()` 阶段一次性 `fetchAll` 并按 `title|artist` 建立字典索引，匹配时 O(1) 查找，批量导入 100 首歌也仅需 1 次数据库查询。

#### 3.2.7 缺失歌曲机制

**存储**：在 CoreData 中新增 `MissingSongReferenceEntity`，记录缺失歌曲的元数据和所属歌单 ID。

**创建时序**（解决 playlistId 依赖问题）：
1. 先创建/获取歌单（新建或找到已有歌单）→ 获得确定的 `playlistId`
2. 遍历歌单内歌曲，匹配本地库
3. 匹配成功 → 添加到歌单
4. 匹配失败 → 用已确定的 `playlistId` 创建 `MissingSongReference`

**标记**：歌单详情页查询歌曲时，同时查询该歌单的 `MissingSongReference`，将缺失歌曲以灰色状态插入列表。

**自动恢复**：在 `ImportService.processFile()` 成功导入新歌曲后，调用 `SyncImportService.checkAndRecoverMissingSongs()`，匹配到则：
1. 将歌曲添加到对应歌单
2. 删除该条 `MissingSongReference`

**跳过播放**：`PlaybackService` 在播放队列中遇到缺失歌曲标记时，自动跳到下一首。

**歌单冲突「替换」的具体行为**：保留原歌单 UUID 和基础属性（createdAt），清空旧歌曲列表后填入新歌曲列表，更新歌单名称/描述/封面/分组信息。这样保持歌单引用稳定，不影响其他依赖该 UUID 的逻辑。

### 3.3 备选方案

#### ZIP 库选择

| 方案 | 优缺点 |
|------|--------|
| **A. 系统 Foundation（推荐）** | iOS 16+ 的 `Data` 可配合 `FileManager` 操作归档文件；无外部依赖；但无原生 ZIP API，需手写或用 `NSData+compression` |
| **B. 引入 ZIPFoundation** | 成熟的 Swift ZIP 库，API 简洁；但引入外部依赖（项目当前零外部依赖） |
| **C. 目录直传（不打包）** | WiFi 同步时逐文件传输不打包；文件导出时才打包。减少打包开销 |

➜ 推荐 **A+C 混合**：WiFi 同步逐文件传输（不打包），文件导出使用系统 `NSData+compression` 或如需引入轻量 ZIP 库。具体在编码阶段确定。

## 4. 影响范围

| 影响区域 | 说明 |
|---------|------|
| WiFiTransferServer | 扩展导出端点，原有上传功能不变 |

**向后兼容**：
- CoreData 新增 Entity 是加法操作，不影响已有数据
- 设置页面入口调整不影响功能
- 不修改任何现有 Entity 字段

## 6. 风险评估

| 风险 | 等级 | 应对策略 |
|------|------|---------|
| WiFi 客户端为全新模块，开发量大 | 🟡 中 | 优先实现文件导出/导入，WiFi 同步作为第二期 |
| ZIP 打包大文件内存占用 | 🟡 中 | 采用流式写入，分块压缩；WiFi 同步逐文件传输不打包 |
| CoreData Migration | 🟢 低 | 新增 Entity 为加法操作，Lightweight Migration 可自动处理 |
| .tunehaven 文件格式兼容性 | 🟢 低 | manifest 含 version 字段，后续版本可向后兼容 |
| 缺失歌曲自动恢复的性能 | 🟢 低 | 仅在新歌曲导入时触发，查询量有限 |
| 项目零外部依赖策略 | 🟡 中 | 优先使用系统 API；如需 ZIP 库则评估是否破例引入 |

### 分期建议

| 期数 | 范围 | 优先级 |
|------|------|--------|
| **第一期** | 文件导出/导入（.tunehaven 格式）+ 冲突处理 + 缺失歌曲机制 + 设置页面重构 | 高 |
| **第二期** | WiFi 设备间同步（服务端导出端点 + 客户端下载） | 中 |
