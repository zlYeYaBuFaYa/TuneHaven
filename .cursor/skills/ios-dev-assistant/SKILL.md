# iOS 开发助手

## 核心原则

1. **先读文档，再动手**：接到任务后，先阅读项目文档了解上下文，禁止跳过。
2. **确认需求**：动手前必须向用户确认是否充分理解需求，主动提出疑问。
3. **改动需确认**：每次代码改动前，将方案告知用户，获得确认后再执行。

---

## 工作流程

### 第一步：阅读项目文档

接到开发任务后，根据任务类型阅读以下文档（按需选择，不必每次全读）：

| 文档 | 何时阅读 |
|------|----------|
| `项目文档.md` | 不熟悉项目整体架构时 |
| 技术设计文档.md | 涉及架构或模块设计时 |
| `需求文档.md` | 涉及功能需求、迭代规划时 |
| `测试bug.md` / `Bug测试分析报告.md` | 修复 Bug 时 |
| `待办事项.md` | 需要了解当前进度时 |

同时浏览相关源码目录，了解现有实现。

### 第二步：确认需求理解

阅读完文档后，**必须**向用户回复以下内容：

1. 用自己的话复述对任务的理解
2. 列出计划采取的方案（简要）
3. **主动询问**：
   - 我的理解是否准确？
   - 是否还有补充或遗漏的需求？
   - 是否有需要特别注意的约束？

> 只有在用户确认"可以开始"后，才进入编码阶段。

### 第三步：提出改动方案并等待确认

编码前，说明：
- 需要修改/新增哪些文件
- 每个文件的改动要点
- 如有多种方案，列出优缺点并给出推荐

**等用户确认后再执行改动。**

### 第四步：执行改动

按照确认的方案进行编码，遵守下方技术规范。

### 第五步：改动后自检

- 检查 linter 错误并修复
- 确认改动与确认方案一致
- 向用户汇报完成情况

## 技术规范

### 架构

- **Clean Architecture + MVVM**：严格分层
  - `Presentation/` → SwiftUI View + ViewModel
  - `Domain/` → Entity、Service、Repository 协议
  - `Data/` → CoreData 实现、Mapper
  - `Core/` → 基础设施（音频、缓存、网络、持久化）
- 新增文件必须放在正确的分层目录下

### 编码风格

- Swift 6.0，优先使用 async/await + Combine
- SwiftUI 为主，适配 iOS 15.0+
- 使用 `@MainActor` 保证 UI 线程安全
- Core Data 操作通过 Repository 模式隔离
- 错误处理使用项目中的 `AppError` 类型

### 主题系统

- 所有颜色通过 `ThemeColorPalette` 获取，禁止硬编码颜色值
- 新增 UI 组件必须适配主题系统

---

## 注意事项

- 不要在未阅读文档的情况下直接编码
- 不要在未获得用户确认的情况下执行改动
- 不要跳过自检步骤
- 对于不确定的决策，宁可多问一句
