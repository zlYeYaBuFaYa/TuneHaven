# iOS 开发助手

## 核心原则

1. **先读文档，再动手**：接到任务后，先阅读项目文档了解上下文，禁止跳过。
2. **需求先行**：审查并完善需求，确认后才进入方案设计。
3. **方案驱动**：编码前必须生成方案文档并通过 Review，禁止无方案编码。
4. **质量闭环**：编码完成后必须通过单元测试和代码 Review，双重质量保障。
5. **文档同步**：提交代码后必须同步更新相关项目文档，保持文档与代码一致。

---

## 工作流程

> **流程总览**：需求审查 → 方案设计 → 方案 Review（≥2 轮） → 编码开发 → 单元测试 → 代码 Review → 提交推送 → 文档同步

### 第一步：需求审查与完善

接到用户的任务描述后，**首先**对需求进行全面审查：

1. **阅读项目文档**（按需选择，不必每次全读）：

| 文档 | 何时阅读 |
|------|----------|
| `项目文档.md` | 不熟悉项目整体架构时 |
| `技术设计文档.md` | 涉及架构或模块设计时 |
| `需求文档.md` | 涉及功能需求、迭代规划时 |

2. **检查需求质量**：
   - **完整性**：是否有遗漏的场景、边界条件、异常处理
   - **一致性**：是否与现有功能/文档存在矛盾
   - **可行性**：在当前架构和技术栈下是否可实现
   - **清晰度**：是否有歧义、模糊表述
   - **合理性**：需求逻辑是否合理，用户体验是否良好

3. **输出审查结果**：
   - 用自己的话复述对需求的理解
   - 指出发现的问题（如有）
   - 提出完善建议（补充遗漏场景、优化交互逻辑等）
   - 给出完善后的完整需求描述

4. **等待用户确认**：用户确认最终需求后，才进入下一步。

> 这一步确保需求质量，避免因理解偏差导致返工。

---

### 第二步：生成方案文档

需求确认后，生成详细的方案设计文档。

**文档路径**：`文档/需求/方案-{功能名称}.md`（目录不存在时自动创建）

**文档模板**：

```markdown
# 方案：{功能名称}

## 1. 需求概述
- 需求背景
- 核心目标
- 预期效果

## 2. 现状分析
- 当前相关代码/模块现状
- 需要修改的文件清单
- 对现有功能的影响范围

## 3. 技术方案
### 3.1 整体设计
- 架构设计（遵循 Clean Architecture 分层）
- 数据流设计
- 关键接口定义

### 3.2 详细实现
- 逐文件说明改动要点
- 新增文件及其职责
- 核心算法/逻辑伪代码

### 3.3 备选方案（如有）
- 方案对比（优缺点）
- 推荐方案及理由

## 4. 影响范围
- 受影响的模块/页面
- 数据库变更（如有）
- 向后兼容性

## 5. 测试要点
- 需要覆盖的测试场景
- 边界条件
- 回归测试范围

## 6. 风险评估
- 潜在风险及应对策略
```

**等待用户确认方案后，进入 Review 阶段。**

---

### 第三步：方案 Review（至少 2 轮）

对方案文档进行严格 Review，确保方案可靠后才进入开发。

**Review 维度**：

| 维度 | 检查要点 |
|------|----------|
| **需求覆盖** | 方案是否完整覆盖所有需求点，有无遗漏 |
| **可执行性** | 技术方案是否可落地，复杂度是否合理 |
| **描述清晰度** | 方案描述是否无歧义，开发者能否据此直接编码 |
| **逻辑合理性** | 数据流、状态管理、业务逻辑是否自洽 |
| **架构合规** | 是否符合 Clean Architecture 分层，依赖方向是否正确 |
| **影响评估** | 对现有功能的影响是否已充分评估 |
| **边界处理** | 异常、空值、极值等边界场景是否已考虑 |
| **性能考量** | 是否存在性能隐患（内存、CPU、I/O） |

**Review 流程**：

1. **第 1 轮（AI 自审）**：按上述维度逐项检查，输出 Review 报告，发现问题则修改方案
2. **第 2 轮（AI 自审）**：对修改后的方案再次全面检查，确认第 1 轮问题已修复，检查是否引入新问题
3. **最终轮（用户确认）**：将 Review 通过的方案提交用户做最终确认

**Review 报告路径**：`文档/review/review-{功能名称}-第{N}轮.md`

**Review 报告模板**：

```markdown
# 方案 Review：{功能名称} - 第 {N} 轮

## Review 结论：通过 / 不通过

## 逐项检查

| 维度 | 结论 | 说明 |
|------|------|------|
| 需求覆盖 | ✅/❌ | ... |
| 可执行性 | ✅/❌ | ... |
| ... | ... | ... |

## 发现的问题（如有）
1. [严重程度] 问题描述 → 修改建议

## 修改记录（第 2 轮起）
- 问题 1：已修复，修改方式为 xxx
```

> Review 未通过时，禁止进入开发阶段。修改方案后重新 Review，直到通过为止。

---

### 第四步：编码开发

方案 Review 通过并经用户最终确认后，按方案执行编码。

1. **严格按方案实施**：不偏离已确认的方案，如需调整须告知用户
2. **遵守技术规范**：参见下方「技术规范」章节
3. **改动后自检**：
   - 检查 linter 错误并修复
   - 确认改动与方案一致
   - 确认代码可编译通过

---

### 第五步：单元测试

编码完成后，**自动**执行单元测试，不需要用户手动触发。

#### 5.1 测试编写规范

- 测试文件位于 `TuneHavenTests/` 目录
- 遵循项目现有测试命名规范（`XxxTests.swift`）
- 使用 XCTest 框架

#### 5.2 测试覆盖维度

| 维度 | 要求 | 说明 |
|------|------|------|
| **行覆盖率** | ≥ 80% | 新增/修改代码的行覆盖率 |
| **分支覆盖率** | ≥ 70% | if/else、switch、guard 等分支路径 |
| **函数覆盖率** | ≥ 90% | 所有 public/internal 方法必须有测试 |
| **正向路径** | 必须覆盖 | 正常输入、预期行为、标准业务流程 |
| **边界条件** | 必须覆盖 | 空值、nil、空数组、极值、临界值（如队列 999 上限） |
| **异常路径** | 必须覆盖 | 错误输入、无效状态、AppError 各 case 触发与传播 |
| **并发安全** | 按需覆盖 | @MainActor 约束验证、async/await 竞态场景 |
| **数据完整性** | 按需覆盖 | CoreData 读写一致性、持久化后再读取验证 |
| **回归验证** | 必须执行 | 运行已有相关测试，确保修改不破坏现有功能 |

#### 5.3 测试执行

1. 使用 `xcodebuild test` 运行相关测试
2. 所有测试必须通过，失败则修复后重新运行
3. 输出测试报告（通过数 / 失败数 / 覆盖率概要）

> 测试未全部通过时，禁止进入代码 Review 步骤。

---

### 第六步：代码 Review

单元测试通过后，**自动**对本次所有改动进行多维度代码 Review。

#### 6.1 Review 维度

| 维度 | 具体检查项 |
|------|-----------|
| **代码风格** | 命名规范（驼峰、语义清晰）、Swift 6.0 惯用写法、格式一致性、无冗余代码/注释、访问控制合理（private/internal/public） |
| **性能** | 时间/空间复杂度合理、无内存泄漏（循环引用）、避免不必要的计算/视图重建、大数据集懒加载、图片/缓存使用合理 |
| **安全** | 输入数据校验、文件访问权限检查、沙盒路径通过 SandboxPathManager 获取、敏感信息不硬编码、URL 安全访问（SecurityScoped） |
| **可维护性** | 遵循 SOLID 原则、DRY（不重复）、低耦合高内聚、代码可读性、模块职责单一、扩展性设计 |
| **逻辑正确性** | 业务逻辑完整、边界处理充分、状态一致性、竞态条件防护、数据流方向正确 |
| **架构合规** | Clean Architecture 分层正确、依赖方向单向（上层→下层）、Repository 模式隔离数据访问、Service 即 ViewModel 模式一致 |
| **错误处理** | 使用 AppError 统一错误类型、错误传播链路完整（Core/Data→Service→View）、ErrorLogger 记录关键错误、用户侧提示友好 |
| **线程安全** | @MainActor 标注正确、UI 操作在主线程、CoreData 双上下文使用正确、Combine sink 中 Task { @MainActor in } 桥接、weak self 防循环引用 |
| **内存管理** | 闭包中 [weak self] 使用正确、大对象及时释放、Combine cancellables 正确存储、图片缓存不超限 |
| **API 设计** | 接口语义清晰、参数合理、返回值设计恰当、async throws 使用一致、与现有 API 风格统一 |

#### 6.2 Review 流程

1. 逐文件检查所有改动，按上述维度输出 Review 结果
2. 对发现的问题按严重程度分类：
   - 🔴 **阻塞**：必须修复（逻辑错误、崩溃风险、安全漏洞）
   - 🟡 **建议**：强烈建议修复（性能隐患、可维护性问题）
   - 🟢 **优化**：可选改进（代码风格微调、命名优化）
3. 修复所有 🔴 阻塞问题和 🟡 建议问题
4. 修复后重新运行单元测试确认无回归
5. 输出最终 Review 结论

**Review 报告路径**：`文档/review/code-review-{功能名称}.md`

> 存在 🔴 阻塞问题时，禁止进入提交步骤。修复后重新 Review。

---

### 第七步：提交代码与推送

代码 Review 通过后：

1. **暂存文件**：`git add` 相关文件（源码 + 测试文件）
2. **提交代码**：使用简洁的 commit message
   - 格式：`type: 简要描述`
   - 常用 type：`feat` / `fix` / `refactor` / `test` / `docs` / `chore`
   - 示例：`feat: 添加歌单批量导入功能`
3. **推送确认**：向用户确认后执行 `git push` 推送到远程仓库

> 推送到远程是不可逆操作，必须经用户确认。

---

### 第八步：同步更新项目文档

代码推送后，**自动**检查并更新以下文档（按改动内容按需更新）：

| 文档 | 何时更新 |
|------|----------|
| `需求文档.md` | 需求完成、需求变更时 |
| `技术设计文档.md` | 架构变更、新增模块、技术方案调整时 |
| `项目文档.md` | 功能变更、项目结构调整时 |

**更新要点**：

- 保持文档与代码实际状态一致
- 新增功能须在对应文档中补充完整描述
- 已完成的需求须在需求文档中更新状态
- 文档更新后单独提交并推送（commit message：`docs: 同步更新xxx文档`）

## 技术规范

### 架构

- **Clean Architecture + MVVM**：严格分层
  - `Presentation/` → SwiftUI View + ViewModel（Service 即 ViewModel）
  - `Domain/` → Entity、Service Protocol、Repository Protocol
  - `Data/` → CoreData 实现、Mapper、AudioMetadataParser
  - `Core/` → 基础设施（音频、缓存、网络、持久化、存储）
- 新增文件必须放在正确的分层目录下
- 依赖方向严格单向：上层可依赖下层，下层不得反向依赖

### 编码风格

- Swift 6.0，优先使用 async/await + Combine
- SwiftUI 为主，适配 iOS 15.0+
- 使用 `@MainActor` 保证 UI 线程安全
- Core Data 操作通过 Repository 模式隔离，使用双上下文（viewContext + backgroundContext）
- 错误处理使用项目中的 `AppError` 类型，通过 `ErrorLogger` 记录
- 所有颜色通过 `@Environment(\.themePalette)` 获取，禁止硬编码
- 文件路径通过 `SandboxPathManager` 获取，禁止硬编码

### 文件组织

- 方案文档：`文档/需求/方案-{功能名称}.md`
- Review 报告：`文档/review/review-{功能名称}-第{N}轮.md`（方案 Review）
- 代码 Review 报告：`文档/review/code-review-{功能名称}.md`
- 单元测试：`TuneHavenTests/` 目录

---

## 注意事项

- 不要在未阅读文档的情况下直接编码
- 不要在未获得用户确认需求的情况下生成方案
- 不要在方案 Review 未通过的情况下开始编码
- 不要跳过单元测试步骤
- 不要在测试未通过的情况下提交代码
- 不要在代码 Review 存在阻塞问题时提交代码
- 不要在未经用户确认的情况下执行 git push
- 不要在提交代码后遗忘文档同步
- 对于不确定的决策，宁可多问一句
- 每一步的产出物（方案文档、Review 报告）都要持久化到对应目录
