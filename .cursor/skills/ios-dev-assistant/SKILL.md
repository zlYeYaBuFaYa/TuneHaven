# iOS 开发助手

## Skill 概述

为 TuneHaven（iOS 本地音乐播放器）提供**从需求到上线的完整开发辅助**。

| 项目 | 详情 |
|------|------|
| 技术栈 | Swift 6.0 / SwiftUI / Clean Architecture + MVVM / CoreData / AVFoundation / Combine |
| 适用场景 | 新功能开发、Bug 修复、代码重构、性能优化、UI/UX 调整、主题适配 |
| 产出物 | 方案文档（`文档/需求/`）、Review 报告（`文档/review/`）、单元测试（`TuneHavenTests/`） |
| 项目文档 | `需求文档.md` / `技术设计文档.md` / `项目文档.md` |

---

## 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **输入质量优先** | 先审查提示词，确保输入清晰、具体、可操作，再进入后续流程 |
| 2 | **先读文档再动手** | 接到任务后先阅读相关项目文档了解上下文，禁止跳过 |
| 3 | **需求驱动** | 审查并完善需求，用户确认后才进入方案设计 |
| 4 | **方案驱动** | 标准任务编码前必须有方案文档并通过 Review |
| 5 | **质量闭环** | 编码后必须通过单元测试 + 代码 Review 双重保障 |
| 6 | **大任务拆分** | 每个阶段启动前评估工作量，超出阈值时拆分为更小粒度的子任务，逐个执行、逐个验收，降低单步复杂度和出错率 |
| 7 | **文档同步** | 第八步完成后**必须自动执行**第九步：逐项检查并更新三份根目录文档，有改动则提交；某份无改动可不修改该文件 |
| 8 | **失败兜底** | 任何步骤连续失败 3 次，暂停流程并向用户汇报 |

## 任务分级

接到任务后**先判断复杂度**，选择对应流程：

| 级别 | 判断标准 | 流程 |
|------|----------|------|
| **轻量** | Bug 修复、样式微调、配置修改、1-2 个文件、逻辑清晰 | ① → ② → ⑤ → ⑥ → ⑦ → ⑧ → ⑨ |
| **标准** | 新功能、多文件重构、架构调整、复杂业务、多模块联动 | ① → ② → ③ → ④ → ⑤ → ⑥ → ⑦ → ⑧ → ⑨ |

```
标准流程：
① 提示词优化 → ② 需求审查 → ③ 方案设计 → ④ 方案Review(≥2轮)
    → ⑤ 编码 → ⑥ 单元测试 → ⑦ 代码Review(≥2轮) → ⑧ 提交推送 → ⑨ 文档同步

轻量流程（跳过 ③④，⑦ 可放宽至 1 轮通过即可）：
① 提示词优化 → ② 需求审查 → ⑤ 编码 → ⑥ 单元测试
    → ⑦ 代码Review(≥1轮) → ⑧ 提交推送 → ⑨ 文档同步
```

> 判断不确定时按标准处理。用户可主动指定级别。

### 特殊情况

| 场景 | 处理方式 |
|------|----------|
| 用户要求跳过某步骤 | 明确告知跳过的风险，用户坚持则遵从并在 commit message 中标注 |
| 同一功能的后续迭代 | 复用已有方案文档，在原文档上追加修改记录，不重新走完整方案流程 |
| 紧急热修复 | 按轻量流程处理，但必须保留测试和代码 Review |

## 任务拆分机制

> 每个阶段启动前先评估工作量，超出阈值时将该阶段拆分为**粒度更小的子任务**，逐个执行、逐个验收。使用 `TodoWrite` 工具追踪子任务状态。

### 拆分触发条件

满足以下**任一**条件即触发拆分：

| 条件 | 说明 |
|------|------|
| **文件数 ≥ 5** | 该阶段预计新增或修改的文件数达到 5 个以上 |
| **跨模块 ≥ 3** | 涉及 3 个及以上不同架构分层或功能模块 |
| **逻辑复杂度高** | 包含多条独立业务逻辑线、复杂状态机、或多层依赖链 |
| **预计耗时长** | 凭经验判断该阶段单次执行难以在合理上下文窗口内完成 |

> **文件数计数口径**：③④ 按方案涉及的模块数替代文件数；⑤ 为新增或修改的源码文件；⑥ 为新增的测试文件；⑦ 为所有待审查的变更文件（源码 + 测试）。

> 不确定是否需要拆分时，**倾向于拆分**。拆分的成本远低于大任务执行中途出错的成本。

### 拆分粒度原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 每个子任务只聚焦一个模块、一个分层、或一条业务线 |
| **独立可验证** | 每个子任务完成后可独立验收（编译通过 / 测试通过 / Review 通过），不需等待后续子任务才能判断正确性 |
| **有序依赖** | 子任务之间如有依赖关系，按依赖顺序排列（如 Domain → Data → Presentation） |
| **粒度适中** | 单个子任务涉及 1~4 个文件为宜，避免过粗或过细 |

### 各阶段拆分策略

| 阶段 | 拆分维度 | 子任务粒度示例 |
|------|----------|---------------|
| ③ 方案设计 | 按需求/模块 | 「需求1-数据层方案」「需求1-UI层方案」「需求2-完整方案」 |
| ④ 方案 Review | 按需求/模块分组 | 「Review-需求1方案」「Review-需求2方案」「全局一致性审查」 |
| ⑤ 编码开发 | 按架构分层 → 模块 | 「Domain层-Entity+Protocol」「Data层-Repository实现」「Presentation层-ViewModel」「Presentation层-View」 |
| ⑥ 单元测试 | 按被测模块 | 「Repository层测试」「Service层测试」「ViewModel层测试」 |
| ⑦ 代码 Review | 按文件组/分层 | 「Review-Domain+Data层」「Review-Presentation层」「Review-测试代码」 |

### 子任务管理规范

**1. 创建子任务清单**：阶段启动前，通过 `TodoWrite` 创建子任务列表，每个子任务包含：
   - 清晰的描述（做什么、涉及哪些文件/模块）
   - 状态标记（pending → in_progress → completed）

**2. 逐个执行**：
   - 同一时间只有**一个**子任务处于 `in_progress`
   - 完成当前子任务并验证通过后，标记为 `completed`，再启动下一个
   - 子任务之间的衔接点需确认前序子任务的产出无误

**3. 子任务验收**：

| 阶段 | 子任务验收标准 |
|------|---------------|
| ③ 方案设计 | 该模块方案完整、与已完成子任务无矛盾 |
| ④ 方案 Review | 该分组 8 项维度全部通过、与已审查分组无冲突 |
| ⑤ 编码开发 | 代码编译通过、linter 无错误、与方案一致 |
| ⑥ 单元测试 | 该模块测试全部通过、无回归 |
| ⑦ 代码 Review | 该文件组所有维度检查通过 |

**4. 阶段汇总**：所有子任务完成后，输出该阶段的整体完成报告，再进入下一阶段。

**5. 子任务失败处理**：
   - 子任务执行失败 → 修复后重试该子任务，不影响已完成的子任务
   - 同一子任务连续失败 3 次 → 暂停流程并向用户汇报，附带失败原因和已完成子任务清单

**6. 拆分调整**：执行中发现子任务划分不当（耦合过紧需合并、粒度仍过大需二次拆分），可即时调整子任务清单并通过 `TodoWrite` 更新，在阶段汇总中说明调整原因

## 工作流程

### ① 提示词优化

> 目标：确保用户输入**清晰、具体、可操作**，为后续步骤提供高质量输入。发现问题时不只指出问题，还要**主动提供可选方案并推荐最优解**，降低用户决策成本。

**审查维度**：

| 维度 | 检查要点 | 问题示例 |
|------|----------|----------|
| 上下文 | 是否指明涉及的页面、模块、场景 | 「按钮没反应」→ 哪个页面的什么按钮？ |
| 具体性 | 是否有具体细节，而非笼统描述 | 「优化性能」→ 什么性能？当前表现如何？ |
| 边界 | 任务范围是否清晰，是否混杂多个需求 | 多个不相关需求混在一段话中 |
| 预期 | 是否说明期望效果或验收标准 | 「改一下 UI」→ 期望什么视觉效果？ |
| 约束 | 是否遗漏技术约束、兼容性、时间等限制 | 需适配特定 iOS 版本但未提及 |

**问题处理策略（核心）**：

对审查中发现的**每一个问题**，必须按以下三步处理：

1. **指出问题**：说明原始描述的不足之处
2. **提供可选方案**：结合项目现状（代码、文档、历史 Bug），列出 2-4 个可能的解读或方向
3. **推荐最优方案**：从中选出最合适的一个，给出推荐理由（参考依据：用户历史反馈、项目优先级、实现成本、用户价值）

**输出格式示例**：

```
问题 1：「优化下播放页面」→ 方向不明确

  可选方案：
  A. 布局优化（按钮位置、间距、信息层级调整）
  B. 动画优化（转场流畅度、手势响应）
  C. 性能优化（渲染卡顿、内存占用）
  D. 主题适配（播放页颜色未跟随主题）

  ➜ 推荐 A：根据历史反馈，播放页布局问题出现最多，优先解决

问题 2：「搜索功能也要改一下」→ 未说明具体改什么

  可选方案：
  A. 增加搜索历史记录
  B. 支持拼音/模糊搜索
  C. 搜索结果排序优化
  D. 歌单内搜索支持

  ➜ 推荐 A：实现成本最低，用户价值最高
```

**其他优化操作**：
- **拆分混合需求**：包含多个独立需求时，拆为子任务并建议优先级
- **具象化描述**：将模糊表述转为具体、可验证的描述
- **补充验收标准**：明确「做到什么程度算完成」

**最终输出**：
- 逐条列出问题 + 方案 + 推荐
- 给出**优化后的完整提示词**（结构化、具体化版本）
- 如有需要用户做选择的问题，明确标注等待用户决定

**等待用户确认（或从推荐方案中选择）后进入下一步。**

---

### ② 需求审查与完善

> 目标：从**业务和技术层面**深入审查需求的合理性和完整性。

**1. 阅读项目文档**（按需选择）：

| 文档 | 何时阅读 |
|------|----------|
| `项目文档.md` | 不熟悉项目架构时 |
| `技术设计文档.md` | 涉及架构或模块设计时 |
| `需求文档.md` | 涉及功能需求、迭代规划时 |

**2. 审查需求质量**：

| 维度 | 检查要点 |
|------|----------|
| 完整性 | 场景是否覆盖全面，边界条件、异常处理是否遗漏 |
| 一致性 | 是否与现有功能或文档存在矛盾 |
| 可行性 | 在当前架构和技术栈下能否实现，成本是否合理 |
| 合理性 | 业务逻辑是否自洽，用户体验是否良好 |

**3. 输出**：
- 复述需求理解 + 指出问题 + 完善建议
- 给出**完善后的完整需求描述**（将写入方案文档「需求概述」）
- 判断任务级别（轻量/标准）

**等待用户确认后进入下一步。**

### ③ 生成方案文档（标准任务）

> 轻量任务跳过 ③④，直接进入 ⑤。

需求确认后生成方案文档，随后**直接进入 ④ Review**，无需用户中间确认。

**大任务拆分**：若方案涉及多个模块或需求点较多，按「任务拆分机制」将方案编写拆分为子任务（如按需求、按架构分层分别编写），逐个完成后合并为完整方案文档。每个子任务完成后检查与已完成部分的一致性。

**路径**：`文档/需求/方案-{功能名称}-{yyyyMMddHHmmss}.md`（目录不存在时自动创建）

**命名规则**：简短中文 + 时间戳后缀，如 `方案-歌单批量导入-20260323143052.md`。时间戳取文件**创建时刻**，精确到秒，格式固定为 `yyyyMMddHHmmss`（14 位数字）。

**多需求合并规则**：当用户的提示词包含多个需求时，所有需求**合并到一份方案文档**中，按需求编号分章节组织，不单独建文件。命名示例：`方案-0320需求优化-20260323143052.md`（按日期或主题概括）。对应的方案 Review 和代码 Review 也各自合并为一份。

**单需求模板**：

```markdown
# 方案：{功能名称}

> 创建日期：YYYY-MM-DD | 状态：草稿

## 1. 需求概述
（第 ② 步确认后的完整需求描述）

## 2. 现状分析
- 相关代码/模块现状
- 需修改的文件清单
- 对现有功能的影响

## 3. 技术方案
### 3.1 整体设计
- 架构设计（Clean Architecture 分层）、数据流、关键接口

### 3.2 详细实现
- 逐文件改动要点、新增文件职责、核心逻辑伪代码

### 3.3 备选方案（如有）
- 优缺点对比、推荐方案及理由

## 4. 影响范围
- 受影响模块/页面、数据库变更、向后兼容性

## 5. 测试要点
- 测试场景、边界条件、回归范围

## 6. 风险评估
- 潜在风险及应对策略
```

**多需求合并模板**：

```markdown

> 创建日期：YYYY-MM-DD | 状态：草稿 | 需求数：N

### 1.1 需求概述
### 1.2 现状分析
### 1.3 技术方案
### 1.4 影响范围
### 1.5 测试要点
### 1.6 风险评估

---
## 需求 2：{名称}
### 2.1 需求概述
...（同上结构）

---
## 需求 N：{名称}
...
```

### ④ 方案 Review（标准任务，≥2 轮）

**大任务拆分**：方案文档涉及多个需求或多个模块时，按需求/模块将方案分组，每组作为一个 Review 子任务，逐组完成 8 项维度审查。所有子任务完成后，再做一次**全局一致性审查**（关注需求间交叉影响、模块间接口一致性、整体架构合规性）。

**Review 维度**（8 项）：

| 维度 | 检查要点 |
|------|----------|
| 需求覆盖 | 是否完整覆盖所有需求点 |
| 可执行性 | 技术方案能否落地，复杂度是否合理 |
| 描述清晰度 | 能否据此直接编码，无歧义 |
| 逻辑合理性 | 数据流、状态管理、业务逻辑是否自洽 |
| 架构合规 | Clean Architecture 分层、依赖方向是否正确 |
| 影响评估 | 对现有功能的影响是否充分评估 |
| 边界处理 | 异常、空值、极值场景是否覆盖 |
| 性能考量 | 是否存在内存/CPU/I/O 隐患 |

**流程**：
1. AI 逐维度自审 → 输出 Review 报告 → 发现问题则修改方案 → 再次自审
2. 重复步骤 1，直到**连续一轮全部通过且无任何问题**
3. **最少 2 轮**（即使第 1 轮无问题，也要做第 2 轮确认）
4. **最多 5 轮**，超限则暂停流程并向用户汇报
5. 自审通过后提交用户做**最终确认**

**报告路径**：`文档/review/review-{功能名称}-第{N}轮-{yyyyMMddHHmmss}.md`（多需求合并时使用概括名称，如 `review-0320需求优化-第1轮-20260323150030.md`）。时间戳取该轮报告**生成时刻**。

**报告模板**：

```markdown
# 方案 Review：{功能名称} - 第 {N} 轮

> 日期：YYYY-MM-DD | 类型：AI 自审 / 用户确认

## 结论：通过 / 不通过

| 维度 | 结论 | 说明 |
|------|------|------|
| 需求覆盖 | ✅/❌ | ... |
| （其余 7 项） | ... | ... |

## 问题（如有）
1. [🔴/🟡/🟢] 描述 → 建议

## 修改记录（第 2 轮起）
- 问题 x：修改方式
```

> Review 未通过，禁止进入编码。

### ⑤ 编码开发

**大任务拆分**：编码前评估改动规模，触发拆分条件时按架构分层拆分子任务。推荐拆分顺序：

```
Domain 层（Entity / Protocol）→ Data 层（Repository / Mapper）
  → Core 层（基础设施变更）→ Presentation 层（ViewModel → View）
```

每个子任务完成后执行自检（编译通过 + linter 无错误），确认无误后再启动下一个。所有子任务完成后做一次**全局自检**确保各层集成正确。

**执行规范**：
1. **严格按方案实施**，如需偏离须告知用户
2. **遵守技术规范**（见下方）
3. **自检**：linter 错误修复 + 确认改动与方案一致 + 编译通过

---

### ⑥ 单元测试

编码完成后**自动执行**，无需用户触发。

**大任务拆分**：被测模块较多时，按模块/分层拆分测试子任务（如「Repository 层测试」「Service 层测试」「ViewModel 层测试」）。每个子任务编写并运行该模块的测试，确认通过后再进入下一个。所有子任务完成后执行一次**全量测试**确保无回归。

**编写规范**：测试文件位于 `TuneHavenTests/`，命名 `XxxTests.swift`，使用 XCTest。

**覆盖维度**：

| 维度 | 要求 | 说明 |
|------|------|------|
| 行覆盖率 | 目标 ≥ 80% | 新增/修改代码，参考目标 |
| 分支覆盖率 | 目标 ≥ 70% | if/switch/guard 分支 |
| 函数覆盖率 | 目标 ≥ 90% | public/internal 方法 |
| 正向路径 | 必须 | 正常输入、标准业务流程 |
| 边界条件 | 必须 | 空值、极值、临界值 |
| 异常路径 | 必须 | 错误输入、AppError 触发 |
| 并发安全 | 按需 | @MainActor、async/await 竞态 |
| 数据完整性 | 按需 | CoreData 读写一致性 |
| 回归验证 | 必须 | 已有测试不被破坏 |

> 覆盖率为参考目标，以测试质量优先。UI 层可适当放宽并说明原因。

**执行**：
1. `xcodebuild test -scheme TuneHaven -enableCodeCoverage YES`
2. 全部通过才继续，失败则修复重跑
3. 输出报告：通过数 / 失败数 / 覆盖率
4. 连续 3 次修复仍失败 → 暂停汇报用户

> 测试未通过，禁止进入代码 Review。

### ⑦ 代码 Review（≥2 轮，最多 5 轮）

测试通过后**自动执行**多维度代码 Review。

**大任务拆分**：改动文件较多时，按架构分层或功能模块将文件分组，每组作为一个 Review 子任务（如「Domain + Data 层 Review」「Presentation 层 Review」「测试代码 Review」）。每个子任务对该文件组执行全部 10 项 Review 维度，发现问题即修复。所有子任务完成后，再做一次**跨模块集成 Review**（关注模块间接口一致性、依赖方向、数据流完整性）。

**拆分后的轮次计数**：跨模块集成 Review 计为第 1 轮；若通过，第 2 轮可采用**增量确认**（仅复查子任务 Review 中修复过的代码 + 跨模块接口），无需完整重走全部 10 项维度。若增量确认发现新问题，则回退到全量 Review。

**Review 维度**（10 项）：

**A. 正确性与安全**

| 维度 | 检查项 |
|------|--------|
| 逻辑正确性 | 业务逻辑完整、边界充分、状态一致、竞态防护 |
| 错误处理 | AppError 统一类型、传播链完整（Core/Data→Service→View）、ErrorLogger 记录 |
| 安全 | 输入校验、SandboxPathManager 路径、SecurityScoped URL、无硬编码敏感信息 |
| 线程安全 | @MainActor 正确、CoreData 双上下文、Combine sink 桥接、weak self |

**B. 质量与规范**

| 维度 | 检查项 |
|------|--------|
| 架构合规 | Clean Architecture 分层、依赖单向、Repository 隔离、Service 即 ViewModel |
| 代码风格 | 驼峰命名、Swift 6.0 惯用法、格式一致、访问控制合理、无冗余代码 |
| API 设计 | 接口语义清晰、参数合理、async throws 一致、与现有风格统一 |

**C. 性能与可维护**

| 维度 | 检查项 |
|------|--------|
| 性能 | 复杂度合理、无循环引用、避免不必要的计算/视图重建、懒加载 |
| 内存管理 | [weak self] 正确、大对象及时释放、cancellables 正确存储 |
| 可维护性 | SOLID、DRY、低耦合高内聚、职责单一、可扩展 |

**问题分级**：
- 🔴 **阻塞**：逻辑错误、崩溃、安全漏洞
- 🟡 **重要**：性能隐患、可维护性问题
- 🟢 **轻微**：风格微调、命名优化、性能小优化

> 三个级别的问题**全部必须修复**，修复后进入下一轮 Review。

**流程**：
1. 第 1 轮：逐文件检查 → 输出 Review 报告
2. 发现任何问题（🔴🟡🟢）→ 修复代码 → 重跑测试确认无回归 → 进入下一轮 Review
3. 重复步骤 1-2，直到**连续一轮全部通过且无任何问题**
4. **标准任务最少 2 轮**（即使第 1 轮无问题，也要做第 2 轮确认）；**轻量任务 ≥1 轮**通过即可
5. **最多 5 轮**，超限则暂停流程并向用户汇报
6. 全部通过后输出最终结论

**报告路径**：`文档/review/code-review-{功能名称}-第{N}轮-{yyyyMMddHHmmss}.md`（多需求合并时使用概括名称，如 `code-review-0320需求优化-第1轮-20260323151500.md`）。时间戳取该轮报告**生成时刻**。

> 存在 🔴 阻塞问题，禁止提交。

### ⑧ 提交代码与推送

1. `git add` 相关文件（源码 + 测试 + 方案文档 + Review 报告）
2. `git commit`，格式 `type: 简要描述`
   - type：`feat` / `fix` / `refactor` / `test` / `docs` / `chore`
3. **向用户确认后**执行 `git push`

> git push 必须经用户确认。

**⑧ 完成后必须衔接 ⑨**：代码提交（及用户确认后的 push）处理完毕后，**不得跳过**第九步；须自动进入文档同步流程。

---

### ⑨ 同步更新根目录三份文档（⑧ 完成后强制执行）

> **时机**：第八步（提交代码，含 push 确认流程）**完成后**，必须**自动**执行本步骤，禁止遗漏。  
> **范围**：项目根目录下三份文档，须**逐项对照本次任务**检查是否需修订：

| 文档 | 检查要点（示例） |
|------|------------------|
| `需求文档.md` | 功能规格、验收描述、迭代规划是否与本次实现一致 |
| `技术设计文档.md` | 服务 API、数据流、UserDefaults、架构说明是否反映代码变更 |
| `项目文档.md` | 核心功能、目录树注释、模块说明是否与仓库现状一致 |

**执行规则**：

1. **三份都要检查**：依次阅读/比对，判断是否需要增删改；不是「有需求才打开需求文档」的被动触发。
2. **有改动才改文件**：某份文档若经判断**确实无需任何修改**，则**不编辑、不提交**该文件（避免无意义 diff）。
3. **有改动则提交**：任一份或多份有更新时，执行 `git add` 对应文件并 `git commit`，建议 message：`docs: 同步更新需求/技术/项目文档`（可按实际改动范围微调说明）。
4. **方案文档状态**：若本次有关联的 `文档/需求/方案-*-*.md`，同步将其状态更新为「已完成」（可与上述三份根文档同一次提交，或随 ⑧ 的提交一并处理，以仓库习惯为准，但须在任务闭环内完成）。
5. **git push**：与 ⑧ 相同，**须经用户确认**后再推送；若 ⑧ 已 push，⑨ 产生新 commit 后再次 push 亦须确认。

**闭环判定**：三份文档均已检查完毕；若有文档更新则已 commit；无文档更新则可在汇报中说明「三份均已核对，无需修改」。

## 技术规范

### 架构

```
Presentation/  → SwiftUI View + ViewModel（Service 即 ViewModel）
Domain/        → Entity、Service Protocol、Repository Protocol
Data/          → CoreData 实现、Mapper、AudioMetadataParser
Core/          → 基础设施（音频、缓存、网络、持久化、存储）
```

- Clean Architecture + MVVM，依赖方向严格单向（上→下）
- 新增文件必须放在正确分层目录

### 编码风格

- Swift 6.0，async/await + Combine
- SwiftUI，部署目标 iOS 16.4+
- `@MainActor` 保证 UI 线程安全
- CoreData 双上下文（viewContext + backgroundContext），Repository 模式隔离
- 错误使用 `AppError`，通过 `ErrorLogger` 记录
- 颜色通过 `@Environment(\.themePalette)` 获取，禁止硬编码
- 路径通过 `SandboxPathManager` 获取，禁止硬编码

### 文件组织

| 产出物 | 路径 | 单需求示例 | 多需求合并示例 |
|--------|------|-----------|---------------|
| 方案文档 | `文档/需求/` | `方案-歌单批量导入-20260323143052.md` | `方案-0320需求优化-20260323143052.md` |
| 方案 Review | `文档/review/` | `review-歌单批量导入-第1轮-20260323150030.md` | `review-0320需求优化-第1轮-20260323150030.md` |
| 代码 Review | `文档/review/` | `code-review-歌单批量导入-第1轮-20260323151500.md` | `code-review-0320需求优化-第1轮-20260323151500.md` |
| 单元测试 | `TuneHavenTests/` | `PlaylistBatchImportTests.swift` | — |

> 多需求合并时，文档内按需求编号分章节组织（需求1、需求2...），保持结构清晰。

## 红线规则

以下规则**不可违反**，无论任务级别：

1. 未经用户确认需求，不生成方案
2. 方案 Review 未通过，不开始编码
3. 方案 Review 必须至少执行 2 轮，发现任何问题必须修复后重新 Review
4. 单元测试未通过，不进入代码 Review
5. 代码 Review 存在 🔴 阻塞问题，不提交代码
6. 标准任务代码 Review 必须至少执行 2 轮，发现任何问题必须修复后重新 Review（轻量任务 ≥1 轮通过即可）
7. 未经用户确认，不执行 git push
8. 第八步完成后必须自动执行第九步：对 `需求文档.md`、`技术设计文档.md`、`项目文档.md` **三份逐一检查**；有改动则更新并 commit，某份确无改动可不修改该文件；须在汇报中说明检查结论
9. 任何步骤连续失败 3 次，必须暂停汇报用户
10. 方案 Review 或代码 Review 超过 5 轮仍有问题，必须暂停汇报用户
11. 产出物（方案、Review 报告）必须持久化到对应目录
12. 触发拆分条件的阶段**必须拆分**后执行，禁止以整体方式硬推大任务
13. 子任务必须通过 `TodoWrite` 追踪状态，禁止无记录地执行
14. 同一子任务连续失败 3 次，暂停该阶段并向用户汇报，附带已完成子任务清单和失败原因
15. 所有子任务完成后，必须执行该阶段的**汇总验收**（全局自检/全量测试/跨模块 Review），不得跳过
