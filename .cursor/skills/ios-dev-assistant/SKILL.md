# iOS 开发助手

## 核心原则

1. **先读文档，再动手**：接到任务后，先阅读项目文档了解上下文，禁止跳过。
2. **确认需求**：动手前必须向用户确认是否充分理解需求，主动提出疑问。
3. **改动需确认**：每次代码改动前，将方案告知用户，获得确认后再执行。
4. **测试驱动收尾**：编码完成后必须编写/运行单元测试，测试通过才可提交。
5. **文档同步**：提交代码后必须同步更新相关项目文档，保持文档与代码一致。

---

## 工作流程

### 第一步：审查用户提示词

接到用户的任务描述后，**首先**对提示词本身进行审查：

1. **检查潜在问题**：需求是否有歧义、遗漏、自相矛盾之处
2. **提出优化建议**：如果发现表述不够精确或可以补充的细节，主动建议用户完善
3. **确认最终需求**：将审查结果和建议反馈给用户，确认后再进入下一步

> 这一步确保需求质量，避免因理解偏差导致返工。

### 第二步：阅读项目文档

根据任务类型阅读以下文档（按需选择，不必每次全读）：

| 文档 | 何时阅读 |
|------|----------|
| `项目文档.md` | 不熟悉项目整体架构时 |
| `技术设计文档.md` | 涉及架构或模块设计时 |
| `需求文档.md` | 涉及功能需求、迭代规划时 |

同时浏览相关源码目录，了解现有实现。

### 第三步：确认需求理解

阅读完文档后，**必须**向用户回复以下内容：

1. 用自己的话复述对任务的理解
2. 列出计划采取的方案（简要）
3. **主动询问**：
   - 我的理解是否准确？
   - 是否还有补充或遗漏的需求？
   - 是否有需要特别注意的约束？

> 只有在用户确认"可以开始"后，才进入编码阶段。

### 第四步：提出改动方案并等待确认

编码前，说明：
- 需要修改/新增哪些文件
- 每个文件的改动要点
- 如有多种方案，列出优缺点并给出推荐

**等用户确认后再执行改动。**

### 第五步：执行改动

按照确认的方案进行编码，遵守下方技术规范。

### 第六步：改动后自检

- 检查 linter 错误并修复
- 确认改动与确认方案一致

### 第七步：单元测试

编码完成后，**必须**执行以下操作：

1. **编写/更新单元测试**：为本次改动涉及的逻辑编写或更新测试用例
   - 测试文件位于 `TuneHavenTests/` 目录
   - 遵循项目现有测试命名规范（如 `XxxTests.swift`）
   - 覆盖正常路径和边界情况
2. **运行测试**：使用 `xcodebuild test` 或相应命令运行相关测试
3. **确认通过**：所有相关测试必须通过，失败则修复后重新运行
4. 向用户汇报测试结果

> 测试未通过时，禁止进入提交步骤。

### 第八步：提交代码

测试全部通过后：

1. 使用 `git add` 暂存相关文件（包括源码和测试文件）
2. 编写符合项目规范的 commit message（格式：`type: 简要描述`）
   - 常用 type：`feat` / `fix` / `refactor` / `test` / `docs` / `chore`
3. 执行 `git commit`
4. 向用户确认是否需要 `git push`

### 第九步：同步更新项目文档

代码提交后，**必须**检查并更新以下文档（按改动内容按需更新，不必每次全改）：

| 文档 | 何时更新 |
|------|----------|
| `技术设计文档.md` | 架构变更、新增模块、技术方案调整时 |
| `项目文档.md` | 功能变更、项目结构调整时 |
| `需求文档.md` | 需求完成、需求变更时 |

更新要点：
- 保持文档与代码实际状态一致
- 文档更新后单独提交（commit message 格式：`docs: 同步更新xxx文档`）

## 技术规范

### 架构

- **Clean Architecture + MVVM**：严格分层
  - `Presentation/` → SwiftUI View + ViewModel
  - `Domain/` → Entity、Service、Repository 协议
  - `Data/` → CoreData 实现、Mapper
  - `Core/` → 基础设施（音频、缓存、网络、持久化）
- 新增文件必须放在正确的分层目录下

### 编码风格

- Swift 6.0，优先使用 async/await + Combine
- SwiftUI 为主，适配 iOS 15.0+
- 使用 `@MainActor` 保证 UI 线程安全
- Core Data 操作通过 Repository 模式隔离
- 错误处理使用项目中的 `AppError` 类型


## 注意事项

- 不要在未阅读文档的情况下直接编码
- 不要在未获得用户确认的情况下执行改动
- 不要跳过自检和测试步骤
- 不要在测试未通过的情况下提交代码
- 不要在提交代码后遗忘文档同步
- 对于不确定的决策，宁可多问一句
- 收到用户提示词时，务必先审查其合理性再执行
