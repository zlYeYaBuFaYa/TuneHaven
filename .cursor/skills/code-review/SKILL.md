# 代码 Review 助手

## Skill 概述

为 TuneHaven（iOS 本地音乐播放器）提供**独立于开发流水线的代码审查能力**。

| 项目 | 详情 |
|------|------|
| 定位 | 独立的代码审查工具，不绑定某个功能的开发流程 |
| 适用场景 | 多轮迭代后的全面审查、特定模块质量评估、变更后的定向检查 |
| 与开发助手的关系 | 开发助手的 ⑦ Code Review 负责功能级 Review（开发流水线中的一步）；本 Skill 负责项目级/模块级 Review（独立活动） |
| 产出物 | Review 报告（`文档/review/`）、修复代码、修复方案（如需） |

---

## Review 模式

接到 Review 需求后，先判断模式：

| 模式 | 触发条件 | 范围 | 示例 |
|------|---------|------|------|
| **全项目** | 用户要求审查整个项目 / 多轮迭代后的全面检查 | 全部源码 + 测试 | 「全项目代码 Review」「项目整体质量检查」 |
| **模块级** | 用户指定某个模块或架构层 | 指定模块的所有文件 | 「Review 一下播放模块」「检查 Data 层代码」 |
| **指定文件** | 用户指定具体文件或目录 | 指定文件 | 「Review 这几个文件」「检查 PlaybackService」 |

> 判断不确定时询问用户。

---

## Review 维度（11 项）

### A. 正确性与安全

| 维度 | 检查项 |
|------|--------|
| 逻辑正确性 | 业务逻辑完整、边界充分、状态一致、竞态防护 |
| 错误处理 | AppError 统一类型、传播链完整（Core/Data→Service→View）、ErrorLogger 记录 |
| 安全 | 输入校验、SandboxPathManager 路径、SecurityScoped URL、无硬编码敏感信息 |
| 线程安全 | @MainActor 正确、CoreData 双上下文、Combine sink 桥接、weak self |

### B. 质量与规范

| 维度 | 检查项 |
|------|--------|
| 架构合规 | Clean Architecture 分层、依赖单向、Repository 隔离、Service 即 ViewModel |
| 代码风格 | 驼峰命名、Swift 6.0 惯用法、格式一致、访问控制合理、无冗余代码 |
| API 设计 | 接口语义清晰、参数合理、async throws 一致、与现有风格统一 |
| 代码整洁 | 无死代码、无未使用 import、无废弃函数/类型、无注释代码块、无冗余文件 |

### C. 性能与可维护

| 维度 | 检查项 |
|------|--------|
| 性能 | 复杂度合理、无循环引用、避免不必要的计算/视图重建、懒加载 |
| 内存管理 | [weak self] 正确、大对象及时释放、cancellables 正确存储 |
| 可维护性 | SOLID、DRY、低耦合高内聚、职责单一、可扩展 |

### 问题分级

- 🔴 **阻塞**：逻辑错误、崩溃风险、安全漏洞、数据损坏
- 🟡 **重要**：性能隐患、可维护性问题、架构违规
- 🟢 **轻微**：风格微调、命名优化、性能小优化

> 三个级别的问题**全部必须修复**。

### 通过标准

- **标准子任务**：11 项 Review 维度全部 ✅，且无任何级别（🔴🟡🟢）的未修复问题
- **回归验证子任务**：上轮修复清单中每一项修复均经验证仍然有效

## 全项目 Review 流程

### 1. 准备阶段

**1.1 了解项目现状**：

- 阅读 `项目文档.md`、`技术设计文档.md` 了解架构和模块
- 统计文件规模（在主 Target 源码目录下搜索 `.swift` 文件数量和行数）
- `git log --oneline -20` 了解近期迭代历史

**1.2 检查已有技术债务**：

查找 `文档/review/` 和 `文档/需求/` 下历史 Review 报告和修复方案。若存在「暂缓/不修改」项：

1. 确认暂缓原因是否仍然成立
2. 原因仍成立 → 维持暂缓，Review 中不重复标记
3. 原因已消失 → 重新标记为待修复问题

### 2. 子任务自动拆分

按 Clean Architecture 分层 + 功能模块自动拆分子任务。**拆分规则**：

| 规则 | 说明 |
|------|------|
| 分层拆分 | 每个架构层至少一个子任务（Core / Data / Domain / App / Presentation） |
| 关注点分离 | 同一层内关注点差异大的目录拆分为不同子任务（如 App 层拆为「入口/DI」和「主题系统」） |
| 粒度控制 | 每个子任务 7~20 个文件，测试类可放宽至 25 个 |
| 底层优先 | 执行顺序从 Core → Data → Domain → App → Presentation → Tests |

**标准拆分模板**（根据实际目录结构调整）：

| # | 子任务 | 涉及目录 | 重点关注 |
|---|--------|----------|----------|
| R0 | 上轮修复回归验证 | 跨层（历史修复涉及文件） | 逐项验证历史修复是否仍有效 |
| R1 | Core - 音频/缓存/持久化/存储 | `Core/Audio`、`Core/Cache`、`Core/Persistence`、`Core/Storage` | 引擎状态机、CoreData 线程安全、沙盒路径 |
| R2 | Core - 网络 | `Core/Network` | 网络层正确性、连接管理、超时、资源释放 |
| R3 | Core - 工具与错误处理 | `Core/Utils` | AppError 体系、ErrorLogger、扩展合理性 |
| R4 | Data 层 | `Data/` 全部 | Repository 实现一致性、Mapper 完整性、上下文使用 |
| R5 | Domain - 实体 | `Domain/Entities` | Entity 设计、Sendable、值类型语义 |
| R6 | Domain - Repository 协议 | `Domain/Repositories` | 接口一致性、async throws 统一、命名规范 |
| R7 | Domain - 业务服务 | `Domain/Services` | 服务耦合度、状态管理、竞态防护、错误传播 |
| R8 | App - 入口/DI/导航 | `App/` 根 + `App/Navigation` | DI 容器完整性、生命周期、导航状态 |
| R9 | App - 主题系统 | `App/Theme` | 线程安全、调色板完整性、壁纸内存 |
| R10 | Presentation - 通用组件 | `Presentation/Common` | 复用性、接口一致性、视图重建优化 |
| R11 | Presentation - 播放器 | `Presentation/Player` + `Root` | UI 状态同步、控制栏交互、Tab 切换 |
| R12 | Presentation - 音乐库与歌单 | `Presentation/Library` + `Playlist` + `Sheets` | 列表性能、批量操作、Sheet 生命周期 |
| R13 | Presentation - 导入与分享 | `Presentation/Import` + `Share` | 导入流程、网络异常、大文件传输 |
| R14 | Presentation - 设置与订阅 | `Presentation/Settings` + `Subscription` | 持久化一致性、订阅状态、功能门控 |
| R15 | 测试代码 | `TuneHavenTests/` + `TuneHavenUITests/` | 覆盖率、Mock、断言质量、测试盲区 |

> **R0 仅在存在历史 Review 修复记录时创建**。若无历史记录，从 R1 开始。

> **模板可调整**：新增模块时添加对应子任务；模块合并/删除时相应调整。每次执行前先 `find` 确认各目录文件数，超出粒度范围时进一步拆分。

### 3. 执行流程

**3.1 执行顺序**：严格线性执行，同一时间仅一个子任务处于 `in_progress`。

```
R0 → R1 → R2 → R3 → R4 → R5 → R6 → R7
  → R8 → R9 → R10 → R11 → R12 → R13 → R14
  → R15 → 跨模块集成 Review → 汇总报告
```

**3.2 每个子任务的执行步骤**：

1. **列出文件清单**：确认涉及的 `.swift` 文件及行数
2. **逐文件审查**：按 11 项维度逐文件检查
3. **记录问题**：按 🔴🟡🟢 分级，附文件名、行号、描述、修复建议
4. **子任务小结**：11 维度结论 + 问题列表
5. **产出报告**：写入独立报告文件

**3.3 轮次规则**：每个子任务独立走「Review → 修复 → 确认」循环。

| 规则 | 说明 |
|------|------|
| 最少轮次 | **2 轮**（即使第 1 轮无问题，第 2 轮做确认） |
| 最多轮次 | **5 轮**，超限暂停汇报用户 |
| 修复后验证 | 每次修复后必须重跑相关测试确认无回归 |
| 增量策略 | 第 2 轮起可仅复查修复点 + 关联代码；发现新问题则回退全量 Review |

**3.4 修复规范**：

| 项目 | 规范 |
|------|------|
| 修复范围 | 按当前子任务文件范围修复，跨子任务问题记录后留到对应子任务 |
| 修复方式 | 🔴🟡🟢 全部直接修复代码 |
| 复杂修复 | 单问题涉及 ≥3 个文件或逻辑复杂时，先生成修复方案（`文档/需求/方案-全项目CodeReview修复-{时间戳}.md`） |
| 测试要求 | 修复后必须 `xcodebuild test` 确认无回归 |
| 修复提交 | 每个子任务独立 commit：`refactor: code review R{x} 修复（{N}项）` |

### 4. 跨模块集成 Review

所有子任务完成后执行：

| 检查维度 | 内容 |
|----------|------|
| 依赖方向 | 无下层→上层反向依赖，Domain 层无 import UIKit/SwiftUI |
| DI 完整性 | 所有 Service 通过 AppDIContainer 注入，无遗漏 |
| 接口一致性 | Repository Protocol 与实现完全匹配 |
| 数据流完整性 | CoreData → Service → View 的 @Published 驱动链完整 |
| 错误传播链 | AppError 从 Core→Data→Domain→Presentation 传播连贯 |
| 主题一致性 | 所有视图通过 `@Environment(\.themePalette)` 获取颜色 |
| 全局状态 | .shared 使用合理，无不必要的全局状态 |
| 死代码 | 无未被引用的 public/internal 接口 |

### 5. 汇总报告

所有子任务 + 集成 Review 完成后，生成汇总报告：

```markdown
# 全项目代码 Review 汇总

> 日期：YYYY-MM-DD | 子任务数：{N} | 总轮次：{M}

## 结论总览

| 子任务 | 结论 | 🔴 | 🟡 | 🟢 | 轮次 |
|--------|------|-----|-----|-----|------|
| R0 回归验证 | ✅/❌ | 0 | 0 | 0 | 1 |
| R1 Core-音频基础设施 | ✅/❌ | ... | ... | ... | 2 |
| ... | ... | ... | ... | ... | ... |
| 跨模块集成 | ✅/❌ | ... | ... | ... | - |

## 修复统计

| 级别 | 发现数 | 已修复 | 暂缓 |
|------|--------|--------|------|
| 🔴 阻塞 | ... | ... | 0 |
| 🟡 重要 | ... | ... | ... |
| 🟢 轻微 | ... | ... | ... |

## 遗留技术债务

| # | 描述 | 暂缓原因 | 来源 |
|---|------|---------|------|
| 1 | ... | ... | 本轮/历史 |

## 代码质量趋势

与上轮对比：新增问题数 / 历史修复回归数 / 整体质量评价（改善/持平/下降）
```

## 模块级 Review 流程

用户指定某个模块或架构层时触发。

### 1. 准备阶段

- 阅读 `技术设计文档.md` 中与该模块相关的章节，了解模块在架构中的定位和职责
- 确认模块与上下游模块的交互关系（依赖哪些接口、被谁调用）
- 查找 `文档/review/` 下该模块的历史 Review 记录，了解已知技术债务

### 2. 确定范围

根据用户描述，按以下规则定位涉及目录：

| 定位规则 | 说明 |
|---------|------|
| 功能模块 | 纵向贯穿：对应的 Domain Service + Presentation 视图 + Core 基础设施。如「播放模块」涉及 `Core/Audio/` + `Domain/Services/PlaybackService.swift` + `Presentation/Player/` |
| 架构层 | 横向切面：该层全部文件。如「Data 层」→ `Data/` 全部 |
| 子系统 | 按实际目录。如「主题系统」→ `App/Theme/` |

> 不确定范围时，列出候选目录及文件数量，询问用户确认。

### 3. 执行

- 文件数 ≤ 20：作为单个 Review 任务，直接执行 11 维度检查
- 文件数 > 20：按「全项目 Review」的拆分规则拆分子任务

### 4. 模块内跨层一致性检查

当模块跨越多个架构层时（如功能模块纵向贯穿 Core → Domain → Presentation），在所有文件审查完成后，执行一次模块内跨层检查：

| 检查维度 | 内容 |
|----------|------|
| Protocol 匹配 | 模块涉及的 Repository/Service Protocol 与实现是否一致 |
| 数据流 | 模块内 CoreData → Service → View 的数据传递是否通畅 |
| 错误传播 | 模块内错误从底层到 UI 的传播链是否完整 |
| 依赖方向 | 模块内各层的依赖方向是否正确（上→下） |

轮次规则、修复规范与全项目 Review 相同。

## 指定文件 Review 流程

用户指定具体文件时触发。

### 1. 上下文理解

- 确认文件所在的架构层和功能模块
- 快速浏览文件的 import 和被引用关系，了解其在架构中的角色

### 2. 执行审查

1. 读取指定文件
2. 按 11 项维度逐文件检查
3. 输出问题列表 + 修复建议
4. 产出报告并持久化到 `文档/review/`

### 3. 修复与确认

- 发现问题 → 修复代码 → 重跑相关测试确认无回归 → 第 2 轮确认
- 至少 1 轮，发现问题则修复后做第 2 轮确认

## 红线规则

1. Review 中发现 🔴 阻塞问题，**必须修复后才能标记子任务通过**
2. 修复代码后**必须重跑测试**确认无回归
3. 同一子任务连续失败 **3 次**，暂停并向用户汇报
4. 单个子任务 Review 超过 **5 轮**，暂停并向用户汇报
5. 子任务必须通过 `TodoWrite` 追踪状态
6. 所有子任务完成后**必须执行跨模块集成 Review**（全项目模式）
7. Review 报告必须持久化到 `文档/review/`
8. 未经用户确认，不执行 `git push`
9. 跨子任务的问题**不得在当前子任务中修复**，记录后留到对应子任务处理（仅适用于全项目模式的多子任务场景）
10. 全项目 Review 完成后，检查 `需求文档.md`、`技术设计文档.md`、`项目文档.md` 是否需同步更新
