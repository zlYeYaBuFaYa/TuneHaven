## 1. 架构

Clean Architecture + MVVM，五层：

```
App           入口、DI 容器、路由、主题、StoreKit 实现、UIKit 相关实现
Presentation  SwiftUI View（Service 直接充当 ViewModel）
Domain        Entity、Repository / 基础设施协议、业务 Service
Data          Core Data Repository 实现、Mapper、音频元数据解析、WebDAV 账户存储
Core          音频引擎、缓存、网络服务器/客户端、Core Data 栈、文件存储、工具类
```

- **依赖方向**：Presentation → Domain ← Data；Core 是基础设施，供各层使用。Presentation 不引用 Core Data；StoreKit 只出现在 App 层 `StoreKitSubscriptionProvider`
- **Service 即 ViewModel**：业务 Service 都是 `@MainActor final class: ObservableObject`，View 通过 `@EnvironmentObject` 直接持有，`@Published` 驱动刷新，不再写转发状态的 ViewModel。例外：`AppleMusicImportViewModel` 是独立 ViewModel
- **Domain 通过协议依赖基础设施**：

| 协议 | 实现 |
|------|------|
| SongRepository / PlaylistRepository / PlaylistGroupRepository / SearchHistoryRepository | `CoreData*Repository`（Data） |
| BackupLibraryApplying | `CoreDataBackupLibraryStore`（Data） |
| AudioEngineProtocol | `AudioEngine`（Core） |
| AudioSessionManaging / NowPlayingManaging | `AudioSessionManager` / `NowPlayingManager`（Core） |
| FileStorageProviding / ImageCacheManaging | `FileStorageService` / `ImageCacheManager`（Core） |
| EmbeddedLyricsReading / LyricsAPIProviding | `EmbeddedLyricsReader` / `LRCLibAPIClient`（Core） |
| ShareServerProviding / ShareClientProviding | `ShareServer` / `ShareClient`（Core） |
| WebDAVClientProtocol | `WebDAVClient`（Core），由 App 层 `DefaultWebDAVClientFactory` 创建 |
| AudioMetadataParsing / WebDAVAccountStoring | `AudioMetadataParser` / `WebDAVAccountStore`（Data） |
| UserPreferencesProviding / CoverImageProcessing / BackgroundTaskProviding | `UserPreferencesStore` / `CoverImageProcessor` / `BackgroundTaskProvider`（App） |
| SubscriptionProviding | `StoreKitSubscriptionProvider`（App） |
| FileImporting | `ImportService`（Domain） |
| CloudDriveProvider | `BaiduNetdiskProvider`（Domain 纯数据）；安装检测 `CloudDriveInstallChecker` 在 App 层 |

- **已知例外**：`ImageCacheManaging` 的方法签名使用 `UIImage`；`PlaylistService.setCustomCover`、`ImportService.processAppleMusicFile` 也接收 `UIImage`

## 2. 依赖注入与启动

### 2.1 AppDIContainer

`TuneHavenApp` 只持有一个 `@StateObject AppDIContainer`。容器属性都是 `let` 或 `lazy var`，不含 `@Published`，不会触发根视图重算。

| 创建方式 | 对象 |
|----------|------|
| `init()` 中按依赖顺序创建 | ThemeManager、AppRouter、SnackbarState、SubscriptionService、MusicLibraryService、PlaylistService、PlaylistGroupService、PlaybackService（内含 PlayQueueService、SleepTimerService）、SearchService |
| `lazy var`（首次访问时创建） | ImportService、WebDAVService、LyricsService、BackupRestoreService、ShareService |
| 引用单例 | AudioEngine、AudioSessionManager、CoreDataStack、ImageCacheManager、NowPlayingManager、FileStorageService、AudioMetadataParser、WebDAVAccountStore、LRCLibAPIClient、AppLogger、ErrorLogger、MigrationManager |

注入环境的对象：ThemeManager、MusicLibraryService、PlaylistService、ImportService、SearchService、AppRouter、SnackbarState、PlaylistGroupService、PlaybackService、AudioEngine、WebDAVService、LyricsService、ShareService、BackupRestoreService、SubscriptionService。

`RootTabView` 的弹窗内容通过 `withFullEnvironment(...)`（`FullEnvironmentModifier`）重新注入常用对象：ThemeManager、AppRouter、MusicLibraryService、PlaylistService、SnackbarState、PlaybackService、AudioEngine、LyricsService、SubscriptionService。

档位变化的响应分两处：`setupSubscriptionBindings()` 订阅 `subscriptionService.$tier` 与 `$isStatusVerified` 的组合并调用 `ThemeManager.applyTier(_:verified:)`；`PlaybackService` 自己订阅 `$tier`，在 `handleTierChange` 中处理无损降级（见 §9）。

### 2.2 启动顺序

```
TuneHavenApp.initialize()
  container.bootstrap()
    MigrationManager.runVersionUpgradeTasks()
    CoreDataStack.load() → MigrationManager.runPostLoadMigrations()
    SandboxPathManager.createAllDirectories()
    await BackupTempDirectory.cleanupOnLaunchBeforeUse()   // 清空三个备份临时目录
    WiFiTransferServer.cleanupTempFiles()
    OpenInImportHandler.cleanupInbox()
  playlistService.initializeSystemPlaylists()               // 首次创建「我喜欢」「最近播放」
  libraryService.loadSongs(按保存的排序) → cleanupOnLaunch()  // 首页排序一致时不再重复加载；清理过期软删除
  playbackService.checkSleepTimerOnForeground()
  recordFirstLaunchDateIfNeeded()                           // app_first_launch_date 缺失时写当前时间
  subscriptionService.loadLocalStatus()                      // 只读缓存的权益 + 本地首次启动日期，不访问 StoreKit
  container.setupSubscriptionBindings()
  await playbackService.restoreLastPlayedSong()             // 必须在订阅状态解析之后
  isReady = true → 处理冷启动期间积压的 onOpenURL
  Task { await subscriptionService.initialize() }           // 后台：购买记录（并写回缓存）、AppTransaction、商品、交易监听
```

回到前台：`checkSleepTimerOnForeground()` + `subscriptionService.refreshStatus()`。进入后台：`audioSessionManager.ensureActive()`。

## 4. 播放

### 4.1 AudioEngine

`AVPlayer` 封装，单例（`private init`，多实例会冲突），实现 `AudioEngineProtocol`。

- 状态机 `PlaybackState`：`idle → loading → playing / paused / error`
- `load(url:)`：检查文件存在 → 扩展名白名单 → `AudioSessionManager.ensureActive()` → `AVURLAsset` 校验 `isPlayable` → 替换 `AVPlayerItem` → 0.5 秒周期时间观察 → 注册播放结束通知
- 事件通过 Combine `playbackEndedSubject`、`timeUpdateSubject` 发出
- `automaticallyWaitsToMinimizeStalling = false`（本地文件无需缓冲）、`allowsExternalPlayback = false`
- 中断开始时暂停并记录状态，结束且 `shouldResume` 时恢复并还原倍速；音频路由断开（拔耳机）时暂停
- 单例没有 `deinit`，提供显式 `cleanup()`

### 4.2 PlaybackService

依赖（全部经 init 注入）：`AudioEngineProtocol`、`PlayQueueService`、`MusicLibraryService`、`PlaylistRepository`、`SongRepository`、`AudioSessionManaging`、`NowPlayingManaging`、`FileStorageProviding`、`UserPreferencesProviding`、`SleepTimerService`、`SubscriptionService`。

主要方法：`play(song:in:)`、`prepare(song:in:)`、`togglePlayPause`、`playNext`、`playPrevious`、`seek`、`skip`、`stop`、`cyclePlayMode` / `setPlayMode`、`setSpeed`、`setSleepTimer`、`toggleCurrentSongFavorite`、`dislikeAndSkip`、`restoreLastPlayedSong`、`ensureCanPlay`。

```swift
enum PlayContext { allSongs(sortBy:), album(name:artist:), artist(name:), playlist(id:), recentlyPlayed(days:), queue }
```

**播放流程**：

```
play(song:in:)
  同一首且在播 → 返回；同一首已暂停 → 继续
  新歌：按 PlayContext 查询歌曲 → queue.replaceQueue → loadAndPlay()
loadAndPlay()
  保存 last_played_song_id → 检查文件 → engine.load → 应用倍速
  → 再次 ensureCanPlay（加载期间可能已降为 Free）→ engine.play
  → libraryService.recordPlay → NowPlayingManager.update
自动切歌：engine.playbackEndedSubject → queue.nextSong(for:dislikes:) → loadAndPlay
```

**倍速记忆**：`speed_memory_mode` 为 0 时读写 `playback_speed`；为 1 时读写 `per_song_speeds[songId]`。切歌时 `applySpeedForSong()` 按模式取值。

**定时关闭**：`SleepTimerService` 用 1 秒 Timer 更新 `remaining`，归零时回调暂停。`PlaybackService` 持有它并转发 `objectWillChange`。回到前台时 `checkOnForeground()` 校正剩余时间。目前没有安排本地通知。

**锁屏与控制中心**：`NowPlayingManager.update(...)` 切歌时全量写入，`updateElapsedTime(...)` 只更新进度字段。远程命令：play → `handleRemotePlay`（先走 `ensureCanPlay`）、pause、next/previous → PlaybackService、changePlaybackPosition → seek。

### 4.3 PlayQueueService

- `queue: [QueueItem]`（含 `isPlayed`）、`currentIndex`
- `replaceQueue`、`appendToQueue`、`insertNext`（满 999 时返回 `.queueFull`）、`removeFromQueue`、`moveInQueue`、`clearQueue`、`saveQueueAsPlaylist`
- `nextSong(for:dislikes:)` 实现需求 §3.2 的四种模式：顺序/列表循环用 `nextUnplayed`（跳过 dislike ≥ `dislikeSkipThreshold`=3）；随机用加权随机 `1/(1+dislike)`；列表循环和随机在全部播放后 `resetAllPlayedMarks()`
- dislike 计数存在 `song_dislikes`，由 `dislikeAndSkip()` 递增，上限 5
- 队列只在内存中

## 5. 音乐库、搜索与歌单

### 5.1 MusicLibraryService

`songs`、`isLoading`；方法 `loadSongs`、`fetchSongsByArtist/Album`、`fetchArtistDetail`、`fetchAlbumDetail`、`fetchRecentlyPlayed(days:page:pageSize:)`、`fetchSong`、`fetchAllSongs`、`toggleFavorite`、`recordPlay`、`updateSongInfo`、`softDelete`、`undoDelete`、`cleanupOnLaunch`。

**软删除**：

```
softDelete(ids:)
  Core Data：softDeleted = true，deletedAt = now
  文件移到 tmp/pending_delete/{uuid}/，返回 UndoToken（songIds、movedFiles、expiresAt）
  30 秒 Timer：
    撤销 → softDeleted = false，文件移回 Music/
    超时 → 物理删除（同一 fileHash 无其他引用时才删文件）+ 删除记录 + 清封面缓存
cleanupOnLaunch() 清理上次进程遗留的过期软删除
```

所有查询默认加 `softDeleted == false`。

**重导软删除中的歌曲**：`CoreDataSongRepository.insert` 按 `fileHash` 取全部同哈希记录，软删除的记录连同歌单链接直接硬删，再按导入的 id 新建；存在未删除记录时只更新它。旧 UndoToken 的提交、撤销按旧 id 已找不到记录，不会影响新歌曲。

### 5.2 SearchService 与 PinyinSearchMatcher

- `search(query:tab:allSongs:)` 在 `Task.detached` 中过滤；艺术家/专辑标签只看对应字段，分组仍来自命中的歌曲
- 音乐库的 300ms 防抖在 `LibraryMainView` 的 `SearchDebouncer`（Combine `debounce`）里；点击历史词绕过防抖
- 历史：`fetchHistory(tab:)`、`saveHistory(keyword:tab:)`、`deleteHistory(id:)`、`clearHistory()`、`clearHistory(tab:)`；每个标签最多 10 条，由 `CoreDataSearchHistoryRepository` 裁剪
- `PinyinSearchMatcher` 匹配顺序：
  1. `trim + lowercased` 后原文 `contains`
  2. 拉丁 query 长度 ≥ 2：全拼从音节起点前缀匹配；首字母串连续包含
  3. 拉丁长度 ≥ 3：对整段全拼或整段首字母做 Levenshtein ≤ 1（长度差 > 1 直接否定）
- 拼音生成：`applyingTransform(.mandarinToLatin)` + `.stripDiacritics`，按非 ASCII 字母数字切音节。结果是展示字符串的纯函数，进程内用 `NSLock` 保护的字典缓存，不落库
- 歌单详情页在 `PlaylistContentView` 里同步调用同一匹配器，每次 body 只 `prepare` 一次，不经过 SearchService

### 5.3 PlaylistService 与 PlaylistGroupService

- PlaylistService：`loadPlaylists`、`fetchDetail`、`createPlaylist`、`updatePlaylist`、`deletePlaylist`、`addSongs`、`removeSongs`、`reorderSongs`、`reorderPlaylists`、`setCustomCover`、`regenerateAutoCover`、`fetchFavorites`、`initializeSystemPlaylists`
- 命名校验在 `createPlaylist` 中：trim → 空则 `playlistNameEmpty`；与系统歌单重名则 `playlistNameDuplicate`
- 自动封面：取前 4 首封面，由 `CoverImageProcessing` 拼 2×2，路径与哈希存 `autoCoverPath` / `autoCoverHash`
- 写操作统一：`performBackground` 写入 → 合并到 viewContext → `loadPlaylists()` 刷新 `@Published`
- PlaylistGroupService：`loadGroups`、`createGroup`、`renameGroup`、`deleteGroup`（组内歌单 `groupId` 置空）、`movePlaylist`、`reorderGroups`

## 6. 导入

### 6.1 ImportService

`isImporting`、`progress: ImportProgress?`（currentFileName、completedCount、totalCount、percentage、estimatedRemainingSeconds）。入口：`importFromFiles(urls:)`、`processWiFiFile`、`processAppleMusicFile`（分享直传用）、`cancelImport`，以及 Apple Music 批量导入用的 `beginBatchImport` / `processBatchExportedFile` / `endBatchImport`。`BackupActivityGate` 保证导入和备份恢复互斥；批量导入整批只占一次锁，批内可并发。WiFi 传输经 `WiFiImportQueue` 串行调用 `processWiFiFile`，闸门忙时等待而不是失败。

**单文件流程 `processFile`**：

```
1. 扩展名白名单（FileStorageService.supportedExtensions） → skippedUnsupportedFormat
2. startAccessingSecurityScopedResource
3. 大小 ≤ 500MB                                           → skippedOversize
4. SHA256 全文件哈希查重（后台线程）                       → skippedDuplicate
   命中 missing/ 占位歌曲（备份恢复的仅元数据曲目）时挂回原记录
5. AudioMetadataParser 解析元数据（缺失项按需求 §3.1 降级）
6. 存入 Documents/Music/（后台线程）：用户文件 copyToMusic；
   本 App 的临时文件（consumeSource，如 Apple Music 导出）moveToMusic，省一次整文件写入
7. CoverImageProcessor 生成 medium 封面（200px）
8. SongRepository.insert
```

结果状态：`success`、`successIncompleteMetadata`、`skippedDuplicate`、`skippedUnsupportedFormat`、`skippedOversize`、`failed`。各步骤日志带 `[Import]` 前缀。

### 6.2 各渠道

| 渠道 | 实现 |
|------|------|
| 文件 / 云盘 | `.fileImporter`（`UTType.allSupportedAudio`）→ `importFromFiles`。云盘 Tab 列出 `CloudDriveRegistry` 中的提供方，`CloudDriveInstallChecker` 用 `canOpenURL(baidunetdisk://)` 检测安装 |
| Apple Music | 见 §6.3 |
| WiFi 传输 | 见 §10.1 |
| 从其他 App 打开 | `onOpenURL` → `OpenInImportHandler` 串行队列处理：`.tunehaven` 交给备份流程，其余走导入；`Documents/Inbox` 在启动时清理 |
| WebDAV | `WebDAVService`：账户 CRUD（密码存 Keychain）、`testConnection`、`connect`、`loadDirectory`（PROPFIND，`WebDAVXMLParser` 解析）、`downloadAndImport`、`cancelDownload`。`WebDAVSessionDelegate` 处理自签名证书。下载：同一个 `WebDAVClient`（actor）以 TaskGroup 并发 3 个，client 内按 id 分别记录下载任务，`cancelDownload()` 取消全部，调用方被取消时经 `withTaskCancellationHandler` 传递；下载循环为 `nonisolated`，不在 actor 上排队；失败或取消时删除目标文件。临时文件放在 `importTemp/webdav-{UUID}/{序号}/{原文件名}`，结束后整个删除。取消后不再派发、不导入，未完成任务标为「已取消」。`connect` 和 `downloadAndImport` 先检查 `canAccess(.webDAVImport)` |

### 6.3 Apple Music 导入

iOS 不提供「音乐」App 里歌曲的文件路径，只给 `ipod-library://` 地址，必须经 AVFoundation 导出一份。导入后的歌曲是独立副本，不依赖「音乐」App。

```
加载：MPMediaQuery（后台线程，过滤云端项和无 assetURL 的 DRM 项）
     → 一次性转成 AppleMusicTrack 快照（id、歌名、艺术家、专辑、时长、搜索键）
导入：beginBatchImport（整批一次锁）
     → AppleMusicDuplicateIndex：歌名 + 艺术家相同且时长差 ≤ 1.5 秒视为已导入，跳过，不导出
     → AppleMusicExporter 按编码导出到 tmp/import_temp/（同时 2 首）
     → processBatchExportedFile：哈希查重 → 移动进 Music 目录 → 入库
     → endBatchImport → libraryService.loadSongs()
```

- **列表用快照**：`MPMediaItem` 的属性每次读取都要查系统媒体库。列表直接用 `MPMediaItem` 时，每次进度刷新都要重新比对整份列表，曲库大时一首要多花约 1.8 秒，所以加载时一次性读成 `AppleMusicTrack`
- **`AppleMusicExporter`**（Core/Audio）：

| 编码 | 方式 | 结果 |
|------|------|------|
| AAC / ALAC | `AVAssetExportSession` Passthrough | m4a，原样 |
| MP3 | `AVAssetReader`（`outputSettings: nil`）逐个拷出压缩包写成文件；`AVAssetExportSession` 不能原样输出 mp3 | mp3，原样（不含 ID3，元数据另从 `MPMediaItem` 读） |
| PCM | Passthrough | wav，原样 |
| 其他 | 依次尝试 Passthrough → m4a、→ caf，最后 `AVAssetExportPresetAppleM4A` 转码 | 转码的歌曲数显示在导入结果里 |

- 歌名、艺术家、专辑和 400px 封面取自 `MPMediaItem`，覆盖文件里解析出的值
- 点「关闭」只收起页面，导入继续在后台完成

## 7. 歌词

`LyricsService` 依赖 `UserPreferencesProviding`、`LyricsAPIProviding`、`FileStorageProviding`、`EmbeddedLyricsReading`、`SubscriptionService`。

**`loadLyrics(for:)` 顺序**：

1. 按歌曲记录的 `lyricsSource`（embedded / file / manual）优先读对应来源
2. 内嵌歌词（`EmbeddedLyricsReader`）
3. `Lyrics/{songId}.lrc`，再按歌名找外部 LRC
4. `auto_match_lyrics` 开启时 `autoMatchOnline`

**在线自动匹配**（需 `onlineLyricsSearch`，Free 时直接返回 nil）：

```
冷却中（lyrics_match_cooldown[songId] 7 天内）→ 跳过
① api.get 精确匹配（歌名 + 艺术家 + 专辑 + 时长）
② api.search 歌名 + 艺术家
③ api.search 仅歌名（艺术家未知时跳过）
④ api.search 简化歌名（去括号、feat.、remix 等）
候选过滤掉 instrumental，优先有 syncedLyrics 的条目
全部未命中 → 记录冷却；网络错误 → 不记录，下次可重试
```

`searchOnline` 在 Free 时抛 `featureRequiresPremium`。其余方法：`saveLyrics`（手动输入）、`importLyricsFile`、`deleteLyrics`、`parseLRC`（`[mm:ss.xx]` 时间戳，非 LRC 文本按纯文本行处理）。API 客户端为 `LRCLibAPIClient`（LRCLIB）。

**显示**：`LyricsTextTransform` 用 `CFStringTransform("Traditional-Simplified")` 做简繁转换，受 `lyrics_simplified` 控制。卡拉 OK 效果是当前行叠加一层 `palette.primary` 文本并用 mask 按行内时间比例从左到右显示。缩放用 `MagnificationGesture`，返回用 `DragGesture`。

## 8. 主题与 iOS 26 外观

### 8.1 主题结构

```swift
struct ThemeStyle: Identifiable { id, displayName, previewColor, palette: ThemeColorPalette, colorScheme }
```

- `ThemeRegistry` 注册 4 套主题（每套一个 `ThemeStyle+Xxx.swift` 扩展）；`ThemeVisualConfig` 决定背景类型，只有星际穹顶是 `CosmicParticlesBackground`，其余为 `palette.background` 纯色
- `ThemeColorPalette` 有 27 个语义色（主色、背景、文字、分隔、渐变、播放器、浮层、标签、`onPrimary` 等）。View 通过 `@Environment(\.themePalette)` 取色，禁止硬编码颜色
- `SemanticColor.danger` 随深浅色切换：浅色 `#C62828`，深色 `#EF4444`；`danger(for:)` 浅色 `#C62828`、深色 `#FB7185`，用于付费墙和订阅错误
- `PaletteContrastTests` 校验正文对比度 4.5:1

### 8.2 ThemeManager

- `@AppStorage(theme_style)` 持久化；`legacyMapping` 把旧 id 映射到 `cloud_white`；无法识别的 id 写回默认
- 免费主题 id：`cloud_white`、`azure_sky`
- `setTheme`：Free 档遇到高级主题直接返回（设置页在无权限时本来就不调用，而是弹付费墙）
- `applyTier(_:verified:)`：记录档位；`verified` 为 true（默认）时调用 `enforceThemeAccess()`，Free 且当前为高级主题时写回 `cloud_white`。未确认的临时 Free 不改主题、不写偏好。`currentTier` 为 `private(set)`，只能经 `applyTier` 修改
- `reloadStoredStyle()`：备份恢复后重新读取主题，同样经过 `enforceThemeAccess`
- `applyToWindows` / `refreshWindows` / `scheduleWindowRefresh`：设置窗口背景色和 `overrideUserInterfaceStyle`。回到前台时不刷新窗口（iOS 会保留属性，刷新反而会与 SwiftUI 渲染冲突导致纯色背景）

### 8.3 LiquidGlassPolicy

最低系统 iOS 18.0，用 iOS 27 SDK 构建。`Info.plist` 不声明 `UIDesignRequiresCompatibility`（iOS 27 SDK 不再支持退回旧设计）。`LiquidGlassPolicy` 只按系统版本分流：

| 系统 | 导航栏 | 自绘 Tab 栏 | 路由 sheet |
|------|--------|-------------|------------|
| iOS 18–25 | 不透明 `palette.surface`；星际穹顶页面为 `.ultraThinMaterial` | `.ultraThinMaterial` | 不透明 `elevatedSurface` |
| iOS 26+ | 不设置 `UINavigationBarAppearance`，用系统玻璃 | `glassEffect`（仍是自绘栏） | 纯色主题不再铺底；星际穹顶仍用 `elevatedSurface` |

页面统一用 `themeNavigationBarSurface()` 设置导航栏背景，避免把系统玻璃盖回不透明。全屏播放器两种路径都保留色板渐变。

## 9. 订阅与门控

### 9.1 SubscriptionService

```swift
@MainActor final class SubscriptionService: ObservableObject {
    @Published private(set) var tier: SubscriptionTier          // .free / .premium
    @Published private(set) var status: SubscriptionStatus      // .trial(daysRemaining:) / .subscribed(expiresDate:) / .lifetime / .expired
    @Published private(set) var products, isPurchasing, restoreError
    func initialize(), canAccess(_:), refreshStatus(), loadProducts(), purchase(_:), restorePurchases()
}
```

- 商品 id：`com.tunehaven.subscription.yearly`、`com.tunehaven.lifetime`，订阅组 `tunehaven_premium`。价格取 StoreKit 的 `displayPrice`，仓库里没有 `.storekit` 配置文件
- `refreshStatus` 解析权益，优先级：买断 > 有效订阅 > 试用 > 过期
- 启动分两步，界面不等 StoreKit：`loadLocalStatus()` 只用上次缓存的权益（`subscription_cached_entitlements`，已过期的订阅视为无效）和本地 `app_first_launch_date` 立即算出状态；随后后台 `initialize()` 读取 `Transaction.currentEntitlements`（并写回缓存），再用 `AppTransaction` 校验。结果不一致时（例如重装后本地日期是新的，但 Apple 记录的首次下载已超过 30 天），经 `$tier` 按到期降级处理。`isStatusVerified` 在 `refreshStatus()` 之后才为 true，`loadLocalStatus()` 给出的档位只是本地推断，不可逆操作（主题降级写回偏好）要等它确认。真机上读取购买记录要 1–2 秒，开发版的 `AppTransaction` 要等数秒才失败，此前两者都在启动路径上，导致白屏「加载中」3–5 秒
- **试用期**：不存到期日。`StoreKitSubscriptionProvider.appOriginalPurchaseDate()` 在 `AppTransaction` 为 `.verified` 时返回 `originalPurchaseDate`，否则回退到 UserDefaults `app_first_launch_date`。按 `Calendar.current` 的 `.day` 计算天数差，小于 `trialDurationDays`（30）为 Premium。Xcode 直装时 `AppTransaction` 不可用，重装会清掉兜底日期；TestFlight / App Store 的 `originalPurchaseDate` 跟随 Apple ID
- 后台 `Task` 监听 `transactionUpdates()`，有更新就 `refreshStatus()`；`deinit` 时取消
- 购买或恢复成功且 `tier == .premium` 时付费墙自动关闭
- `AppURLs`：`privacyPolicy`（`https://tunehaven.app/privacy`）、`manageSubscriptions`（`https://apps.apple.com/account/subscriptions`）

### 9.2 门控位置

| PremiumFeature | 拦截位置 |
|----------------|----------|
| `losslessPlayback` | `PlaybackService.ensureCanPlay(_:)`，被 `play`、`prepare`、`togglePlayPause`、`loadAndPlay`（加载后、开播前再验一次）和锁屏 `handleRemotePlay` 调用 |
| `premiumTheme` | 设置页上锁；`ThemeManager.setTheme`；`applyTier` → `enforceThemeAccess` |
| `webDAVImport` | 设置页上锁；`WebDAVService.connect`、`downloadAndImport` |
| `onlineLyricsSearch` | `LyricsService.autoMatchOnline`（静默跳过）、`searchOnline`（抛错） |

是否无损由 `Song.isLossless` 判定（规则见需求 §3.1）。

**无损拦截细节**：

- 拒绝时设置 `losslessBlockedSong`，不调用 `engine.play()`
- 付费墙弹出位置：播放器未全屏时由 `RootTabView` 延迟 0.35 秒弹出；全屏播放器打开时由 `PlayerView` 在 `fullScreenCover` 之上弹出
- `playNext` / `playPrevious` 遇到无损：`parkOnBlockedSong` 暂停并保留为 `currentSong`
- 降为 Free（`handleTierChange`）：只暂停正在播放的无损，有损不受影响
- `restoreLastPlayedSong`：Free 且上次是无损时不写入 `currentSong`，也不发拦截信号，但记为 `pendingLosslessRestore`；之后 `handleTierChange` 收到 `.premium` 且 `currentSong` 仍为空时补回（不播放），随即清空待恢复项
- 外部打开备份交接期间（`externalBackupTakesModal == true`），延迟弹出的付费墙让出模态层，但 `ensureCanPlay` 照常拦截

## 10. 局域网服务：WiFi 传输与分享直传

两者都基于 Network Framework（`NWListener` + `NWConnection`）自写 HTTP 服务器，端口不同，可同时存在。

### 10.1 WiFiTransferServer（端口 8080）

`@MainActor ObservableObject`：`isRunning`、`serverAddress`、`password`、`connectionState`、`transferProgress`、`securityAlert`。网页模板为 `Core/Network/wifi_transfer.html`，地址可生成二维码（`QRCodeGenerator`）。

```
POST /auth    校验密码。错误按 IP 累计，满 5 次冷却 30 秒（期间返回 429）
              成功后由 WiFiTransferSession 签发内存 token
POST /upload  密码开启时必须带 Authorization: Bearer <token>，否则 401 且不写文件
              写入 tmp/wifi_upload/{UUID}-{原文件名} → onFileReceived → WiFiImportQueue
```

**WiFiImportQueue**（`@MainActor`，传输页的 `@StateObject`）：

- 依赖协议 `WiFiFileImporting`（`isImportBusy`、`processWiFiFile`），由 `ImportService` 实现；`isImportBusy` 读 `BackupActivityGate.isBusy`
- 文件逐个处理：闸门忙则每秒重查，空闲后调用 `processWiFiFile`；处理完（无论结果）删除上传临时文件
- 队列排空且有新入库时调用一次 `onImported`（传输页传入 `libraryService.loadSongs()`）
- 处理 Task 强持有队列直到排空，关闭传输页后已收到的文件继续导入
- 上传落盘名加 UUID 前缀，同名文件不互相覆盖；`cleanupTempFiles()` 启动时同时清空 `wifi_upload/`

- token 在停止服务、重新生成密码、设置自定义密码、再次 `start` 时作废；密码关闭时上传不校验 token
- 传输中有新 IP 连接时发出 `securityAlert = .newDeviceWhileTransferring`
- `wifi_password_enabled` 控制是否启用密码

### 10.2 分享直传（端口 8090）

- 发送端 `ShareServer`（`ShareServerProviding`）：`start()` 等到 listener `.ready` 才返回；二维码内容为 `http://{ip}:8090?token={sessionToken}`，每个请求都校验 token
- 接收端 `ShareClient`（`ShareClientProviding`，URLSession）。下载文件按 `{audio|cover|lyrics}_{序号}.{扩展名}` 本地命名，发送端 `Content-Disposition` 只用来取扩展名，且须在白名单内（音频为支持格式、封面 jpg/jpeg/png、歌词 lrc/txt），否则用默认扩展名（dat / jpg / lrc），不使用发送端的任何路径字符
- `ShareService` 同时实现 `ShareDataSource`，为服务器提供数据；服务器和客户端通过工厂闭包注入

| 方法 | 路径 | 内容 |
|------|------|------|
| GET | /info | 设备名、歌曲/歌单数量、总大小 |
| GET | /songs、/playlists | 摘要列表 |
| GET | /songs/{i}/meta | 单曲完整元数据（`SongExportData`） |
| GET | /songs/{i}/audio、/cover、/lyrics | 文件流 |
| GET | /playlists/{i}/songs | 歌单内歌曲 |

```
发送：prepareSendSongs / prepareSendPlaylists → 启动服务 → 返回二维码内容 → stopSending
接收：connectAndAnalyze(qrContent:)
        拉取列表 → buildSongIndex → matchSong → ShareAnalysis（含 insufficientDiskSpace）
      executeReceive()
        逐首下载音频/封面/歌词 → ImportService 标准导入
        → 创建分组和歌单（同名加「-2」）→ 关联已有歌曲
      cancelReceive()
```

- 匹配：标题 + 艺术家相同为 `fuzzyMatch`（跳过传输）；再加专辑和时长一致为 `exactMatch`
- 文件分块流式读写；`Content-Disposition` 用 RFC 6266 编码中文文件名；路由正则缓存在 `static let routePatterns`
- 接收时用 `BackgroundTaskProviding`（`beginBackgroundTask`）保持后台传输；失败时清理客户端状态和临时文件
- 预览页目前按下载体积阈值提示空间，还没有直接读取 `insufficientDiskSpace`

## 11. 本地备份与恢复

### 11.1 组件

| 组件 | 职责 |
|------|------|
| `BackupRestoreService`（`@MainActor`） | 设置页状态：`estimate`、`export`、`inspect`、`restore`、`cancel`、`stageExternalPackage`、`presentRestore` |
| `BackupExporter` | 曲库快照 → 备份目录 |
| `BackupPackageCodec` | JSON 编解码 + 调用 ZIP |
| `ZipStoreArchive`（Core） | 只读写 ZIP store（method 0），不依赖 Domain 类型；超过 ZIP32 约 4GB 或遇到其他压缩方式时报错 |
| `BackupPlanner` | 纯函数，生成合并 / 替换 / 仅偏好的提交计划 |
| `BackupSongMatcher` | 歌曲、歌单冲突匹配（规则见需求 §3.10） |
| `BackupCommitter` | 复制新文件、调用 apply、失败回滚 |
| `CoreDataBackupLibraryStore` | 实现 `BackupLibraryApplying`：一次 background context `save` 写歌曲、分组、歌单 |
| `BackupPreferenceStore` | 读写 4 个偏好键 |
| `BackupActivityGate` | 备份与导入互斥 |
| `BackupTempDirectory`（Core） | 三个临时目录的清理 |

### 11.2 包格式

ZIP store，扩展名 `.tunehaven`（UTI `com.tunehaven.backup`）。内容：`manifest.json`、`preferences.json`、`groups.json`、`playlists.json`、`songs.json`，以及 `audio/`、`covers/`、`lyrics/`。`formatVersion` 必须为 1。偏好只允许 `theme_style`、`play_mode`、`speed_memory_mode`、`lyrics_simplified`。

### 11.3 恢复提交

```
解包到 tmp/backup_extract/
→ 只复制到尚不存在的新路径（音频 Music/backup-{id}.ext，封面 backup_{id}_medium.jpg）
→ 停止播放
→ 一次 apply（Core Data 单次 save）
→ 成功后写偏好 → ThemeManager.reloadStoredStyle()
→ 删除不再被引用的旧音频、歌词、封面（这一步失败不回滚曲库）
```

- 复制失败、校验失败或 `apply` 抛错：删除本次新建的文件，不写偏好，抛 `backupCommitRolledBack`
- 取消只在复制循环中和 `apply` 之前检查
- 取消标志：关闭任意备份页时 `cancel()` 置位；`beginWork()`（导出/恢复）开始时复位，`inspect` 在空闲（非 `isBusy` 且无解包进行中）时也复位，否则关过页面后预览会一直报「已取消」。页面关闭时仍在进行的恢复保持取消
- 封面、歌词路径在对应文件复制成功后才写入，避免包里缺附件时清掉本地封面
- 替换模式丢弃自建歌曲、歌单、分组；系统歌单若指向已删除分组，改回未分组
- 缺音频的歌曲 `fileRelativePath` 用 `missing/` 前缀，`Song.isAudioMissing` 为真，列表显示「未找到」；之后导入同一首时按哈希或同一套匹配规则挂回，保留 id、收藏和播放次数

### 11.4 临时文件与外部打开

**三个目录**（`tmp/` 下）：

| 目录 | 生命周期 |
|------|----------|
| `backup_export` | 确认未超 4GB 后，导出前在后台删除旧包再写新包；快照失败或超限时保留上一份。`isBusy` 防止并发导出 |
| `backup_incoming` | 从外部打开的副本。恢复成功、取消或关闭恢复页后删除；交接被打断没弹出恢复页的副本留到下次冷启动 |
| `backup_extract` | 解包目录，随准备好的包一起丢弃（不在恢复成功后立刻删，方便同页重试） |

冷启动时 `bootstrap` 先 `await BackupTempDirectory.cleanupOnLaunchBeforeUse()` 清空三个目录，之后才 `isReady` 并处理积压的 `onOpenURL`，所以清理一定发生在任何导出或分享之前。这次清理不碰 WiFi、导入或分享直传的临时目录。

**外部打开交接**（`TuneHavenApp.presentStagedBackup` + `AppRouter`）：

1. `stageExternalPackage` 只复制到 `backup_incoming`，不弹页；切到设置 Tab
2. 没有任何模态时立即 `presentRestore`
3. 否则 `relinquishModalsForExternalBackup()` 置 `externalBackupTakesModal = true` 并清空根 sheet：
   - 播放器开着：先让它收起自己的 sheet，0.5 秒后 `closePlayer()`，再 0.5 秒后尝试弹出
   - 只有根 sheet：0.5 秒后直接尝试弹出
   - 0.5 秒长于付费墙的 0.35 秒延迟
4. 尝试弹出时若播放器或根 sheet 又出现了：不弹，复位标志，snackbar 提示稍后从「文件」打开（不在之后自动重试，避免和用户刚打开的页面抢模态）
5. 3 秒兜底：同一 token 仍未走到 `presentRestore` 时复位标志，不删副本
6. 后一次打开会使前一次的 token 失效

设置里的「从备份恢复」不走这套交接。

## 12. 并发与持久化

### 12.1 并发

- 所有 ObservableObject Service、`AudioEngine`、`WiFiTransferServer`、`ShareServer` 都是 `@MainActor`
- 耗时工作：Core Data 写入走 `performBackground`；文件 IO、哈希、搜索过滤走 `Task.detached` 或后台队列
- Combine 回调里用 `Task { @MainActor in ... }` 回到主线程；`NWConnection` 回调同理
- 线程安全：拼音缓存用 `NSLock`；`ImageCacheManager` 的磁盘读取与占用统计在串行 `fileQueue` 上执行

### 12.2 Core Data

`CoreDataStack`（单例）提供 `viewContext`（主队列，UI 读取）和 `backgroundContext`（私有队列，`init` 时创建）。

```
performBackground { ctx in ... }
  backgroundContext.perform → 执行 block → save
  → 捕获 didSave 通知 → viewContext 显式 mergeChanges
  → 在主队列恢复调用方
  出错时 rollback
```

两个上下文都用 `NSMergeByPropertyObjectTrumpMergePolicy`；`viewContext.automaticallyMergesChangesFromParent = true` 作为兜底。读操作在 viewContext，写操作一律走 `performBackground`。`MigrationManager` 负责版本升级任务和加载后的数据迁移。表结构见《项目文档》。

## 13. 沙盒文件与缓存

所有路径通过 `SandboxPathManager` 获取，禁止硬编码。`Song.fileRelativePath` 只存相对 `Documents/Music/` 的路径。

```
Documents/                 不会被系统清理，参与 iCloud 备份，可在「文件」App 中看到
  Music/                   音频文件（备份恢复的文件名为 backup-{id}.ext）
  Lyrics/                  LRC 歌词
  error.log / app.log      日志（各 5MB，超出时改名为 .old）
  Inbox/                   系统放入的外部打开文件（启动时清理）
Library/Application Support/   不会被系统清理，参与 iCloud 备份
  CoverImages/             歌曲封面（medium 200px），唯一存储
  PlaylistCovers/          歌单封面（自定义与自动拼图），唯一存储
Library/Caches/            空间不足时可能被系统清理
  CoverImages/ PlaylistCovers/   旧版本封面目录，启动时由 CoverStorageMigration 迁走后删除
tmp/
  pending_delete/          软删除中的文件
  wifi_upload/             WiFi 上传临时文件（启动时清理）
  import_temp/             导入临时文件
  backup_extract/ backup_export/ backup_incoming/   见 §11.4
  export_temp/ sync_extract/                        启动时创建，当前没有代码使用
```

**图片缓存（ImageCacheManager）**：

- 内存：`NSCache`，`totalCostLimit` 50MB，内存警告时清空
- 磁盘：只读 `Application Support/PlaylistCovers/{key}`，其次 `Application Support/CoverImages/{key}`；文件由 `CoverImageProcessor` 写入，缓存层不写、不删、不淘汰
- `store(image:forKey:)` 只更新内存并发 `.imageCacheDidUpdate`；歌曲封面、拼图封面、自定义歌单封面写盘后都会调用
- 设置页「封面占用」统计两个目录大小，不提供清理
- 迁移：`CoverStorageMigration` 在 `bootstrap()` 的 `createAllDirectories()` 之后执行，逐个移动旧 Caches 目录的文件；旧 `CoverImages` 中与歌单封面同名的拼图副本丢弃；目标已存在时保留目标；单个失败保留旧目录待下次启动重试
- 封面尺寸：导入时由 `CoverImageProcessor` 生成歌曲封面 medium（200px）；歌单自定义封面为 large（400px）。`ThumbnailSize` 还定义了 small 100、original ≤1024，目前未使用

**索引**：SongEntity 建有 byArtist、byAlbum、byImportDate、byFileHash、bySoftDeleted；PlayRecordEntity 建有 bySongId、byPlayedAt。

### 15.2 日志

- `ErrorLogger`：写 `Documents/error.log`，格式 `[ISO8601] [错误码] 上下文 - 描述 at 文件:行号`

- 传播链：Core/Data 抛底层错误 → Service 转成 `AppError` 并记录 → View 展示 `localizedDescription`
